# 待办状态与提醒偏好设计

原始需求设计按当前需求修订（2026-09-22）。完整保留状态语义与验收矩阵；最终实现及实际验证边界见 [R5 交付记录](R5_ACCEPTANCE.md)，不能以需求存在代替验收通过。

## 目标

让总览里的预算提醒和固定支出待办可以被持续处理，而不是每次刷新都重新出现：用户能标记已读、稍后处理、关闭某类提醒，并在业务事实重新变成待处理时看到一次新的提醒。

本轮不增加模型工具。待办是否成立、属于谁、何时重新出现，全部由服务端依据预算、流水和固定支出事实确定。

## 用户闭环

1. 用户在“本月关注”看到预算或固定支出待办。
2. 可直接进入业务页面，也可标记“已读”或选择“稍后处理”。
3. 刷新、重新登录后状态保持；稍后时间到达后待办重新出现。
4. 用户可关闭某一提醒类型，并在提醒设置中重新开启。
5. 已处理的业务事实再次失效时，生成新的待处理状态，不被旧的已读记录永久隐藏。

## 范围

首轮只覆盖现有 `NextActions` 已经展示的两组确定性事实，并细分为六种待办类型：

- `budget_near_limit`：预算使用达到 80%，但未用完。
- `budget_limit_reached`：预算额度用完。
- `budget_overspent`：预算超支。
- `recurring_upcoming`、`recurring_unreviewed`、`recurring_review_required`：固定支出即将到期、逾期待核对、原关联已不再合格。

交付内容：

- 服务端统一生成待办，不再由前端自行拼装业务状态。
- 持久化单项状态：未读、已读、稍后处理。
- 持久化类型偏好：开启或关闭。
- 总览展示未读/已读状态、稍后时间、类型设置和恢复入口。
- 数据库迁移、备份结构版本、架构及运行文档同步更新。

## 明确不做

- 不发送邮件、短信、系统推送或即时通信消息。
- 不增加后台事件队列、定时消费者或 Redis。
- 不做模型生成的提醒，不让模型决定预算是否超支或固定支出是否完成。
- 不自动修改预算、关联流水、确认“本期未发生”。
- 不做固定支出自动发现；它属于后续独立迭代。
- 不重新添加仓库内测试文件；如后续需要恢复自动回归，单独确认范围。

## 状态语义

### 稳定身份

- 预算：`预算记录 ID + 月份 + 币种`。删除后重建预算会得到新 ID，不继承旧状态。
- 固定支出：`周期项目 ID + 预计日期`。同一项目不同期次互不覆盖。
- 类型关闭按用户和提醒类型保存，不影响其他用户和其他类型。

客户端不提交可信身份字符串。写入状态时提交结构化来源和服务端返回的 `fact_token`；服务端重新计算当前事实、校验用户归属和 token 后再写入。

### 已读

“已读”只隐藏当前待办实例，不改变预算、流水、周期项目或核对状态。默认列表优先显示未读，用户可展开已读项目。

### 稍后处理

客户端仅提交固定选项，由服务端确定绝对到期时间：两小时后、明天 09:00、七天后 09:00。日历选项使用现有规划口径 Asia/Shanghai，存储为 UTC；不得使用浏览器时钟计算可信期限。“七天后”指当地日期加七天后的 09:00，不是严格 168 小时上限。例如 9 月 22 日 08:00 选择该选项，到期为 9 月 29 日 09:00，七天一小时是合法结果。不接收任意自定义期限；超过日期支持上限返回参数错误。

到期前从默认列表隐藏，到期后投影为未读，不需要后台任务。返回值包含服务端时间与绝对到期时间；到期后的状态版本令牌使用不同的到期阶段，旧请求不能再次隐藏已经到期的项目。重复操作返回首次冻结的到期时间，不能从重试时间重新延后。

### 类型关闭

关闭类型后，该类型不进入默认列表，但业务事实仍正常计算。重新开启后按各项当前未读、已读或稍后状态恢复展示，不自动清空单项状态；关闭偏好不等于业务完成。

### 重新打开

业务事实与用户阅读状态分开版本化。每个已有用户状态的来源保留 `generation` 和最近业务事实，包括事实不成立的阶段；重新成立或提醒类型变化时递增 generation，用户状态重置为未读。不依赖用户是否打开过总览。预算等级降低但仍告警也视为类型变化；同一等级内金额变化只更新展示，不反复重开。名称等文案变化不重开。

在影响已有状态的业务写事务内同步维护事实：预算创建、修改、复制、删除；流水导入、撤销、分类修改；关系确认、撤销；固定支出配置、暂停恢复、匹配解除、未发生确认及撤回。同步发生在业务修改 flush 后、提交前，与业务变更一同回滚。包括退款原消费改类影响的其他月份、关联流水被关系排除等跨期依赖；不能仅按正在查看的月份筛选。无关联状态的来源保持按需计算、默认未读，无需预生成全部历史期次。

所有上述写路径必须覆盖受影响来源与跨期依赖。正常可计算期间不得只写“已脏”标记后等读取时重算，否则连续两次写入之间的消失和重现仍会丢失。按受影响月份复用一次共享金额计算，避免每条状态重复读取账本。该同步计算带来的写入耗时纳入验收。

如果仅待办计算超过既有确定性容量上限，业务写入仍按自身规则执行；在同一事务中将受影响的已有状态标为 `unknown`，首次进入 unknown 时递增 generation 和 revision、清除旧已读/稍后状态并记录原因及开始时间。连续处于 unknown 不重复重开，旧令牌始终无效；不得把 unknown 当作事实消失，也不得根据截断数据生成金额。这里只处理明确的容量错误，不吞掉数据库错误或程序异常；unknown 标记无法原子保存时事务仍失败。

unknown 期间展示“暂时无法计算”，禁止新的单项状态操作，不影响类型偏好修改和其他可用组。恢复完整计算后，当前成立的事实以一次新的未读实例出现；不成立则转为已知的不活跃事实。保留“期间变化未完整追踪”的结构化原因供验收核对，不声称复原期间每次变化。GET 可以只读投影该恢复结果；下一次相关业务写入或单项操作按下述归一化规则将其落库。每次 unknown 到 known 只递增一次代次。

`fact_token` 绑定用户、来源、generation、当前提醒类型和规则版本；固定支出的到期阶段由服务端日期推导，到期当日即为待核对。时间从即将到期推进到待核对时，旧类型状态不再适用，无需后台写入。GET 只读，不创建状态、不更新“已观察”标记，也不清理记录。

GET 和所有相关写路径共用一个无副作用的归一化函数，以持久化状态、完整当前事实和本次请求固定的服务端时间为输入，返回有效事实签名、generation、revision、用户状态和期限。时间类型推进、unknown 恢复等尚未落库的变化在投影中生成有效新版本；重复读取同一底层状态时得到相同版本，不逐次累加。事实签名只包含会影响待办状态的语义字段，不包含名称等展示文案。

单项状态写入取得用户锁后先归一化，用有效版本校验请求，再将归一化事实签名、提醒类型、代次与新用户状态原子保存；业务写入也保存同一归一化结果。若发生归一化重开与用户操作，版本分别按规则推进，但同一时间转换只能消费一次。下一次名称修改等无语义变化的写入读到已保存的新签名，必须保持已读状态和代次。稍后到期同样先归一化为未读并清除已消费期限，之后用户选择已读不得再次被该旧期限失效。

### 并发与重试

状态请求携带 `fact_token`、`expected_state_version` 和客户端 UUID `operation_id`。状态版本令牌包含持久化 revision 与稍后到期阶段；首次无记录使用版本 0。任何用户操作和业务驱动重开都递增 revision；恢复未读保留行，避免删除再建后旧版本重新有效。

状态写入沿用现有业务顺序：先锁用户，再读取当前事实和状态，校验版本后条件更新。业务写入和待办写入使用同一用户锁串行化；写路径使用锁后新读取的数据，不复用认证前固定的旧快照。多行修改按稳定来源顺序执行。

幂等回执按用户与 operation_id 唯一保存，绑定完整请求摘要，与状态修改原子提交。同 key 同请求只返回原回执、不再次修改状态；同 key 不同请求返回冲突。回执可在当前事实变化后继续查回，前端收到回执后重新读取列表，不用旧回执覆盖新状态。类型偏好写入使用同一机制；缺省偏好版本为 0，首次创建同样执行条件校验。

## 数据设计

新增三张表，迁移版本为 `20260922_0015`：

### `attention_states`

- `user_id`
- `source_type`
- `source_id`
- `source_date`
- `attention_type`
- `generation`、`fact_signature`：实例代次及最近的确定性业务状态
- `fact_status`：`active`、`inactive` 或 `unknown`；unknown 不等价于 inactive
- `unknown_reason`、`unknown_since`：当前不可计算原因及起始时间
- `last_tracking_gap`：最近一段不可计算区间及原因，恢复后保留，不保存账务明细
- `revision`：用户状态与业务重开的单调版本
- `state`：`unread`、`read` 或 `snoozed`
- `state_attention_type`：用户操作时的提醒类型，保护时间推进后的新类型
- `snoozed_until`
- `created_at`、`updated_at`

用户、来源类型、来源 ID 和日期构成唯一身份；所有读取和写入都附带 `user_id`。source_id 指向不可复用的预算或项目身份。源对象删除时在同一业务事务中删除对应状态；事实暂时不成立或不可计算时必须保留状态行。用户删除级联清除。为用户、来源和日期建立索引，并约束版本正数、状态枚举及 snoozed 状态必须有到期时间；unknown 必须带原因和开始时间且不得保留已读/稍后状态。

### `attention_preferences`

- `user_id`
- `attention_type`
- `enabled`
- `version`
- `updated_at`

缺少记录等价于开启。修改携带 `expected_version`，防止多个标签页互相覆盖。

### `attention_operations`

- `user_id`、`operation_id`：联合唯一键
- `request_digest`：包括操作种类、目标、期望版本与参数
- `receipt`：最小冻结回执，包括已接受版本和绝对稍后期限，不包含账务明细
- `created_at`

本轮不按时间清理回执，避免旧请求过期后重新执行；用户删除时级联清除。

备份包含三张表并同步结构版本。恢复准备保留状态、偏好与回执；恢复后的稍后状态按当前服务端时间投影，过期项目重新未读。没有外部事件重放。必须实际验证备份还原后状态、偏好、回执去重及恢复准备重复执行。

## 服务与接口

新增独立的 `domain/attention.py`、`db/attention_repository.py`、`services/attention.py` 和 `api/attention.py`。复用现有预算和固定支出的确定性计算，不复制账务算法。共享事实计算不得反向调用写服务，避免业务服务与待办服务循环依赖。

预算与固定支出分别使用独立的可重复读会话，认证后始终以服务端用户身份读取。禁止在同一个 AsyncSession 上并发查询。每组在自己的快照内合并事实、状态与偏好，返回组内读取时间和版本；不承诺两组构成同一瞬时快照。

响应按组返回 `status: ready | unavailable`、安全错误码、可重试标志和数据。单组失败时 HTTP 200 返回另一组可用数据；两组均失败或公共认证/基础设施不可用时返回统一错误。前端对失败组显示读取失败，计数标明不完整；不得将失败或容量拒绝解释为空列表，也不得清除该组持久化状态。重试允许只请求失败组。

接口契约：

- `GET /api/v1/attention?month=YYYY-MM-01&group=all`：group 可为 all、budgets、recurring；返回组状态、未读项、已读项、稍后项、关闭类型计数及偏好，并附 `server_time` 和 `next_refresh_at`。稍后项包含来源、token、状态版本和到期时间，可提前恢复。
- `GET /api/v1/attention/preferences`：独立读取当前用户的六类偏好，不依赖事实计算；两组均不可用时仍能读取和修改设置。
- `POST /api/v1/attention/state`：标记已读、稍后处理或恢复未读；携带事实 token、状态版本、operation_id，返回冻结操作回执。
- `POST /api/v1/attention/preferences/{attention_type}`：启用或关闭类型，携带偏好版本和 operation_id。偏好关闭优先于单项状态；重新开启保留仍有效的已读和稍后状态，仅恢复该类型的可访问性。

返回项包含稳定来源、展示数据、当前状态、`fact_token` 和业务页面定位参数。金额仍使用 Decimal 字符串；页面不得根据百分比重新判断业务类型。

错误契约：

- 当前事实不存在：`attention_not_found`。
- 当前事实超过计算容量：`attention_unavailable`（422），保留来源并要求减少计算范围或等待数据调整，不伪装为 404；幂等成功回执仍可重放返回。
- token 已过期：`attention_stale`，页面刷新列表，不自动重放操作。
- 稍后时间非法：`invalid_snooze_time`。
- 偏好版本冲突：`attention_preference_conflict`。
- 用户状态版本冲突：`attention_state_conflict`，保留操作意图并重读，用户重新操作时使用新 key。
- 相同操作 key 的请求内容不同：`attention_operation_conflict`。
- 冲突均为 HTTP 409，事实不存在为 404，参数错误为 422；基础设施不可用为 503。网络结果不明时只允许用原 key 和原请求重试。

## 前端交互

重构 `NextActions`，只读取待办接口：

- 卡片主操作仍进入预算或固定支出页面。
- 次操作提供“已读”“稍后处理”；选项为“两小时后”“明天 09:00”“七天后 09:00”，展示 Asia/Shanghai 时间。
- 提供“稍后处理”列表，显示期限并支持提前恢复未读；已读列表也可恢复未读。
- 接受回执后重读对应分组；结果不明保留原请求和 key。按用户、月份、分组及请求序号隔离响应，旧响应不得覆盖新列表。
- 列表读取不得清除结果未明的原操作及 key；确认前阻止替代写入。定时刷新不依赖前次读取成功，首次读取失败仍注册网络恢复监听。
- 原请求在发送前写入用户隔离的 sessionStorage，覆盖状态和偏好操作；存储失败不得发送。切页、刷新和认证暂时过期保留原 key、版本和请求，恢复后由用户显式重试，不自动发送。确定成功或确定拒绝后清理；主动退出清理，用户不匹配不得重放。损坏或不可读记录阻止新写入，迟到结果只能清理同一 operation_id。
- 读取状态、错误和新鲜度按组保存；一组成功不得清除另一组失败。账本变更通知同时使总览金额和待办失效，刷新期间旧快照明确标记。
- 顶部显示未读数量，并提供“显示已读”“稍后处理”和“提醒设置”；分组失败时不显示误导性的全量零计数。
- 服务端 next_refresh_at 取最早稍后到期时间或下一业务日边界。页面可见时按服务端时间差设置定时重读，最迟每 60 秒刷新可见分组；隐藏时暂停，重新可见、获得焦点或网络恢复时立即重读。浏览器休眠后以服务端结果为准，在线可见页面到期后 60 秒内更新。
- 关闭某类提醒必须二次确认，文案明确“只隐藏提醒，不修改账务事实”。
- 375px 下操作纵向排列；键盘焦点在操作完成后移动到下一项或空状态。

中英文文案同时交付，不新增口号、解释性大段文本或独立设置页面。

## 验收标准

功能必须满足：

- 两个用户看到并修改的待办完全隔离。
- 已读状态跨刷新和重新登录保持，且不修改任何预算、流水或固定支出事实。
- 稍后项目在到期前隐藏、到期后重新出现；旧 token 写入被拒绝。
- 类型关闭跨登录保持，重新开启后按原有效状态恢复当前仍成立的项目。
- 预算告警等级升级会重新未读；固定支出从已匹配变为需重核会重新未读。
- 删除后重建预算不继承旧状态；不同固定支出期次不串状态。
- 多标签页偏好冲突不会静默覆盖。
- 预算已读后，在没有 GET 的情况下依次降至阈值以下、再升回原等级，仍重新未读；固定支出从需重核变合格再失效也重新未读。普通名称修改不重开。
- 同一事实的两个标签页分别执行稍后和已读，只接受符合当前状态版本的操作；恢复未读之后重试旧成功请求只返回旧回执，不覆盖新状态。同 key 不同内容明确冲突。
- 业务事实更新与状态写入竞争时按用户锁串行处理；业务事务回滚时 generation、状态和回执均不得留下部分提交。
- 有已读待办的月份从 10,000 笔导入至 10,001 笔时，满足原业务约束的导入成功，相关状态原子进入 unknown，旧令牌被拒绝；超限期间分类修改不因提醒计算超限被阻断。无关状态不变，数据库故障仍完整回滚。
- 超限后撤销导入回到可计算范围，当前成立的事实只重开一次，未成立的事实保持不活跃，并保留追踪缺口记录。重复 GET 不递增有效版本；归一化落库后再 GET 与后续无关修改不再次重开。
