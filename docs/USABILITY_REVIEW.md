# 连续使用评审与改进方案

评审日期：2026-09-16。对象：main 未提交工作区的当前程序。下方问题与操作记录保留修复前基线；U01—U14 已在当前 main 工作区实现，最新验证见末尾「修复验收」。未提交。

## 环境和方法

使用 `bankpilot_planning_v1` 隔离 PostgreSQL 与 `planning-ui@example.com` 合成账户，不修改共享业务库。先通过真实导入接口准备过去两个月的生活流水，再在已登录页面连续操作。Chrome 查看桌面现状；用户切换 Chrome 后，改用独立后台浏览器，避免抢占用户窗口。

准备 76 笔新模拟交易，加上原有 4 笔，共 80 笔；包括 4 个账户、CNY/USD 两种币种，工资、房租、宽带、餐饮、超市、会员、本人转账、跨月退款和同批疑似重复。准备后账户有 11 条预算、8 个固定支出项目。随后通过页面上传 3 行补录文件，新增 2 笔、重复 1 笔，最终 82 笔。基础样本与预算/项目初始化用接口完成，不能称为 80 次手工页面录入。

页面验证采用连续任务，而非逐个按钮孤立点击。桌面查看总览、预算、固定支出布局；以 390×844 视口检查手机月报、导航和账本，完成后恢复默认视口。没有重跑负载测试、断网测试、真实模型或真实银行文件认证。

## 优先改进：使用逻辑

### U01 · P1 · 总览与局部任务应有各自范围

**复现**：月度总览 → 导入一天补录 → 查看结果 → 总览。金额显示一天的 97 元，提醒却是整月 764 元餐饮。

**方案**：总览保留用户最后明确选择的总览期间。批次入口只改变账本临时范围，不改总览。账本顶部展示“本批新增 2 笔 · 9 月 16 日”，提供“返回本月账本”。如果总览允许跨月范围，预算区明确要求选择提醒月份，不能默取开始月份而让用户猜。

**验收**：完成任意日期补录后，总览仍保持原期间；每个金额区都能明确识别时间、账户、币种范围。金额变化能归因于新增数据或关系调整。

### U02 · P1 · 先核对影响金额的记录，再判断超支

**观察**：转账确认前支出 14,751，确认转账和退款后是 12,052。首页“实际支出”没有同时突出待确认关系。标题“暂无待核对关系”也只能表示候选结果，不能证明数据无异常。

**方案**：金额下显示短状态，如“按当前核对结果统计 · 1 项关系待确认”，并提供入口；候选影响只能显示为待核对，不能提前扣减。需要明确区分“未核对完”和“已经核对但预算超支”。未分类/其他大额应先引导核对分类，不直接鼓励给“其他”扩预算。

**验收**：从总览能发现会影响统计的未处理事项，确认后展示本次调整前后金额或明确差额；不将候选当成确定账务事实。

### U03 · P1 · 手动关联按角色选择，约束前置

**观察**：两个下拉列表混入所有交易；切换关系类型保留旧选择；同批重复记录在提交后才报错。

**方案**：从账本交易详情进入“关联退款/转账/重复”，固定当前交易作为一端。另一端使用独立搜索，按方向、币种、时间和现有冲突筛选。切换关系类型清理不适用选择，保留用户搜索词。确认前展示两笔交易及本次对统计的影响。错误放在对应字段旁。

**同批重复是需求边界**：当前规则只处理跨批重复，不应直接放宽自动去重。若支持同批纠错，应新增明确的人工排除及撤回流程，保存理由与证据；否则在选择阶段说明限制，并引导撤销批次、修正源文件后重新导入。不能建议删除原始证据或自动忽略其中一笔。

**验收**：收入不能作为退款的原支出；已知不符合规则的组合提交前即可解释；成功后清理已完成组合并保留下一次操作上下文。

### U04 · P1 · “未发生”不能忽略眼前的相符扣款

**观察**：音乐会员存在日期、商户、金额相符的 18 元候选，仍可用无差别确认框标记未发生。

**方案**：有强匹配候选时，确认框显示该候选，首选“核对这笔”；仍允许用户明确选择“不是这次扣款，标记未发生”，保留撤回。不以强匹配为由自动关联。

**验收**：无候选和有候选时的确认信息有区别；不会只因为误点一次就把待办隐去。

### U05 · P2 · 预算参考必须带资料覆盖范围

**观察**：十月额度编辑显示九月 764 元参考，但样本只覆盖至 9 月 16 日；用户容易当成完整月支出。

**方案**：显示“九月已导入支出 764 · 最新交易 9/16 · 完整性未确认”。可以查看该月来源范围；不要默认线性外推或称为推荐额度。预算零支出也区分“有数据且无此类消费”和“该月尚未导入”。

**验收**：用户设置下月额度前能看到参考的来源月份和覆盖局限；无需打开说明文档。

### U06 · P2 · 月报需要回答问题并提供行动

**观察**：多笔月报仍只有收支三个数；“4 项大额支出”不能直接查看。每次更新生成一个时间戳版本，缺少明显的当前版本与差异。

**方案**：报告按“本月收支 → 主要变化/支出 → 需要核对 → 后续动作”组织。大额提示可打开冻结证据列表；预算超支和固定支出状态如纳入报告，必须在生成时一起冻结，不能在旧报告里混入实时结果。新增数据尚未形成完整月份时注明截至日期。旧版本折叠，选定报告置于历史之前。调整后分类分布须由服务端统一口径生成，不能复用原始分类假装一致。

**验收**：每个提示能在两次点击内看到对应证据；同月版本能区分新旧，过期提示只出现一次；历史报告内容不受新分类和关系修改影响。

## 页面排列建议

总览：标题及期间 → 紧凑分币种收支 → 待处理事项（数量、优先级、入口）→ 预算摘要与近期固定支出 → 最近流水。数据范围收纳为一行状态和可展开详情，不重复安排“导入账单”和“补充账单”两个同等主入口。

账本：标题及新增/导入 → 期间和筛选标签 → 条数与当前筛选范围 → 交易列表 → 点击侧栏看来源、分类和关系。大额核查跟随具体交易展开，不在长列表底部复制整段记录。

预算：月份及设置入口 → 分币种已设额度/已计入支出/未覆盖支出 → 超支优先的紧凑分类列表 → 选中分类详情面板。编辑金额复用面板，不把表单插到顶部、详情插到底部来回跳。

固定支出：月份及新增 → 待核对数量、即将到期数量 → 状态过滤 → 按预计日期排列的列表 → 核对/计划变更面板。修改、暂停、结束放次级菜单；主要按钮随状态变为“核对扣款”或“查看记录”。

月报：月份及当前版本 → 一处数据截至/过期状态 → 收支、变化和可点击事项 → 导出 → 历史版本 → 折叠技术证据。默认阅读顺序应支持用户做判断，而不是先选数据库记录。

## 实施顺序与边界

1. **先修范围与误操作**：U01、U03、U04、U07。四项分别解决看错期间、选错关系、误隐藏待办、点击后找不到结果。保留现有账务校验，不增加兼容回退。
2. **再统一信息布局**：U08—U14。为预算/固定支出复用一套详情面板、筛选标签和状态展示，不额外堆叠多套弹窗或页面。
3. **最后补决策内容**：U02、U05、U06。确认统计口径与快照边界后增加范围状态、月报证据入口及明确的版本差异。

本次已工作的路径应保留：真实导入去重、转账/跨月退款调整、固定扣款关联、未发生撤回、预算复制不覆盖、跨页草稿保留、历史快照不可变。这些不是重写业务层的理由。

月份控件的 Playwright 填值没有完成页面状态切换，随后内嵌浏览器打开原生月份弹层时崩溃。因此十月页面通过显式 URL 打开继续验证；不把该控件现象直接认定为产品缺陷，也不宣称原生月份控件已通过本轮验证。PDF 输出、移动端实际设备、真正首次空账户上手、弱网与保存冲突不在本轮实测范围，后续单独验收。
