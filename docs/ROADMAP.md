# 后续路线

当前已实现能力和未验收边界见 [当前状态](CURRENT_STATE.md)，现行契约见 [架构](ARCHITECTURE.md)。本文件仅描述尚未交付的方向，不重复已完成阶段的实施过程。

## 发布前基础工作

- 认证真实脱敏的微信/支付宝导出样本，核对数量、金额、状态、币种、退款及排除原因；合成样本不能代替来源认证。
- 补齐当前待办的完整容量、事务竞争、恢复和浏览器矩阵，以及月报任务竞争与数据库短时中断验证。
- 使用代表性数据验证备份恢复，明确保留策略、数据导出与注销安排。恢复清理聊天历史仍须明确确认，不能改写备份本体。
- 验证前后端同批发布、协议拒绝及生产链路；不得用本地通过替代生产验收。
- 当前不恢复仓库内测试脚本。若需要固定回归入口及 CI 集成，另行确认范围。
- 模型质量验证按 [模型验证与边界](MODEL_VALIDATION.md) 单独安排，真实模型调用需明确授权。

## R6：固定支出候选发现

实施契约与验收矩阵见 [R6 设计](R6_DESIGN.md)；以下保留路线级边界。

用户例子：“帮我找出可能每月都在扣的订阅。”

- 首版只识别月付：按同账户、币种、规范化商户及日期/金额模式形成候选。至少三个不同月份的观测作为起始规则，阈值经样本评估后确定。
- 每个候选显示形成依据、实际扣款月份、金额波动和已知缺口。数据不足返回“证据不足”，不推断已停扣或漏扣。
- 用户可以忽略、修改后创建、关联到已有项目。候选不得自动创建计划，也不自动关联历史期次。
- 确认建项使用独立提案，显示完整参数和来源证据；重复确认幂等。已有项目、暂停项目和已忽略候选参与重复检查。
- 模型可以解释候选，但确定性规则负责候选证据及约束，不引入独立训练服务。

先准备人工标注的独立样本；指标定义为候选精确率 `正确候选数 / 所有提出候选数`，目标至少 90%，同时报告正确候选、误报、漏报、召回率和样本覆盖。无候选时精确率不可计算，不能记作 100%。调节阈值的样本与最终评估样本分开，报告各类失败而不只报总分。这个数是待验证目标，不能以少量合成样本包装成真实准确率。

无重复建项是确定性硬门槛，使用可重复的确认/重试/并发脚本验证。真实样本不足时可以完成规则与交互实现、合成验收，但默认不启用自动发现，并保留真实样本验收缺项；其他阶段继续推进。

年付识别、金额预测和自动确认另行评估，不与月付发现一起交付。

## R7：事件与通知

基于现有站内待办状态，为需要后台处理的事件添加事务内记录和幂等消费；业务事务回滚不产生有效事件，重试不重复生成有效通知。数据库恢复后保留关闭偏好并抑制旧事件重放，只有新状态变化触发后续处理。

接入固定支出发现候选事件；会话查询变化订阅使用现有持久会话，不将全局修订号变化广播成每条查询的提醒。

只有站内待办确实被使用，且用户明确需要离站提醒时，才追加一个外部渠道。届时单独交付时区/安静时段、用户订阅、退订、重试与投递回执；默认消息不含敏感交易详情。不同时接入邮件、短信和多个 IM。

门槛：同一事件无重复有效待办，事务回滚不发通知，关闭后不再投递。将事件竞争、恢复准备与投递重试加入固定回归。外部渠道未启用时，明确交付范围仅为站内状态与事件处理。

## 演进边界

继续复用现有确定性消费计算、证据版本、用户锁和幂等回执，不增加相互独立的金额算法。持久任务沿用 PostgreSQL 租约与领取令牌，未经测量不引入 Redis、队列或服务拆分。

下一步先补齐待办和发现建项的验收缺口，再做助手只读入口；外部通知以明确渠道需求为进入条件。模型解释不能代替候选证据、金额计算、权限判断或用户确认。

公开多用户共享账本、银行直连、资金操作、投资推荐和原生移动应用不在当前路线内。
