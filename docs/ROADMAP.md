# BankPilot 后续迭代路线

规划日期：2026-09-17。文档状态：最终版。代码基线：`main@e03a88a`。R1 已在工作区实现，交付状态见 [R1 记录](R1_ACCEPTANCE.md)；其余阶段按各自验收门槛推进。

执行责任：所有阶段的设计细化、实现、验证、问题修复和交付记录由 Codex 完成，按技术依赖与验收门槛推进。真实样本、外部服务访问等条件缺失时，记录具体缺项并继续独立可执行的工作。

## 产品方向

把 BankPilot 做成能持续使用的个人账单核查助手：导入后知道资料范围，发现影响金额的问题，能追问到证据，并在明确确认后完成有限的管理操作。

主要价值是减少查账、解释差额和核对固定支出的人工步骤。模型负责理解问题和选择受限工具，账务计算、证据一致性和操作权限由程序保证。不扩展到银行资金操作、投资建议或完整家庭资产管理。

核心使用路径：**导入 → 核对 → 问清消费 → 解释变化 → 确认计划 → 下次继续处理。**

## 阶段安排

| 迭代 | 用户目标 | 交付范围 | 验收门槛 |
| --- | --- | --- | --- |
| R0：真实使用基线 | 确认格式支持和恢复能力 | 样本认证、空账户流程、固定回归和恢复记录 | 已声明支持的样本核对一致，恢复与隔离检查通过 |
| R1：消费证据 | 查清某类消费的逐笔构成 | 消费/预算统一入口、退款原消费、双版本和流水定位 | 两条工具路径均可用，独立金额预期与固定回归通过 |
| R2：连续使用 | 刷新或隔天继续查询 | 会话保存、历史结果、提案恢复与删除 | 不重放旧写入，历史与当前事实区分明确 |
| R3：流水查找 | 找到指定条件的交易 | 结构化筛选、确定性匹配及流水定位 | 条件可解释，结果完整且用户隔离 |
| R4：消费比较 | 查清两个期间的支出差额 | 同口径分类差额、消费/退款分解及证据下钻 | 分类差额之和等于总体差额，覆盖范围明确 |
| R5：待办状态与订阅 | 记住已读、稍后处理和关闭偏好 | 复用现有待办，持久化状态与类型订阅 | 状态恢复、撤回重开和去重通过 |
| R6：固定支出发现 | 从重复扣款建立周期项目 | 月付候选、形成依据、忽略与确认建项 | 独立样本评估通过，无重复建项 |
| R7：事件与通知 | 接收有效状态变化 | 事务事件、幂等消费、恢复抑制及可选外部渠道 | 不丢失有效事件、不重复生成通知，退订有效 |

R0 是贯穿路线的交付基础，外部样本缺失只阻塞依赖它们的验收。每个迭代独立完成设计、实现与验收，按 R0 至 R7 的顺序推进。

## R0：真实使用基线

建立来源格式支持矩阵、可重复验收环境和恢复记录，覆盖真实微信/支付宝导出、任务竞争及生产链路。

- 按来源、导出入口和格式版本记录真实脱敏样本，核对交易数量、金额、状态、币种、退款及排除原因。脱敏必须保留交易关联结构，不能破坏去重验证所需编号。
- 从空账户验收完整流程：创建账户、预览、导入、纠错、撤销、重新导入。
- 验证月报中断、租约耗尽、删除与完成竞争、数据库短时中断；使用代表性数据恢复并记录耗时和可恢复范围。
- 建立仓库内可重复运行的合成验收入口，固定输入、独立预期和隔离库准备/清理步骤；真实样本本体不入库，只记录脱敏认证结果。R1 及后续阶段持续扩展这套验收。
- 首次对外或生产发布前完成备份位置、保留/删除策略、用户数据导出与注销安排，以及前后端同批发布验收。

交付为一份可核对的支持矩阵和运行验收记录。无法获取某来源样本时继续标记“待认证”，不能用合成样本填成“已支持所有格式”。

## R1：消费追问与证据闭环

按 [R1 设计](R1_DESIGN.md) 交付共享计算、助手交互和验收，当前结果见 [交付记录](R1_ACCEPTANCE.md)。

提供单月、单分类、单币种的实际消费与构成查询。消费工具与预算工具返回同结构的消费引用，统一提供明细入口。跨月退款展示原消费；多轮通过明确选定的结构化范围继承上下文，多范围歧义时澄清。

查询及翻页同时校验 `ledger_revision` 与 `calculation_version`。账本变化或计算规则升级后要求重新查询，不混用旧金额与新明细。规则版本由共享计算模块统一声明，不与迁移版本或预算额度版本混淆。固定回归覆盖两种工具路径、双版本失效、退款/排除规则、负净支出和用户隔离，并使用独立预期金额。

验收覆盖从一次提问到具体证据的完整流程，记录操作数、成功/失败场景和接口/模型耗时，作为后续改进基线。

## R2：会话与操作结果恢复

用户例子：“昨天问到一半，今天接着看。”

- 服务端保存会话、消息、明确选中的查询范围、账本/计算版本、当时汇总与操作 ID；增加用户归属、列表分页和删除能力。
- 将历史查询明确标为“当时结果”。首版不保存完整逐笔历史快照：账本或计算版本任一不一致时，历史明细显示不可重建，可发起一次新查询；不能用新规则重算后冒充旧证据。
- 模型继续对话时重新读取需要的当前事实，不能把昨日金额当作今日结果。会话摘要不能改变已确认的业务对象、提案状态或权限。
- 恢复待确认提案时以数据库状态、有效期和目标版本为准；刷新、网络重试和继续聊天均不能重新创建或执行已完成操作。
- 控制发送给模型的历史长度。商户、备注和历史消息仍是数据，不能提升工具权限。
- 明确消息保留时间、单会话/单用户配额、删除与备份保留关系；恢复演练纳入新增数据表。

门槛：刷新、重新登录、取消、过期、并发确认及用户切换通过；删除后不可再访问相应会话；旧回执不能覆盖后续预算变更。上述路径连同规则升级后的历史读取纳入持久回归脚本，恢复演练覆盖会话与提案状态。

## R3：受限流水查找

用户例子：“九月在某商户的那笔 200 元扣款在哪？”

- 增加明确的日期范围、账户、币种、商户文本和金额条件；由模型输出结构化筛选，界面显示可修改的条件。
- 商户首版使用规范化后的确定性文本匹配，不凭模型推断不同名称属于同一商户。
- 查找结果首先是原始流水及关系状态，不直接命名为“实际消费总额”。要统计调整后消费，应走专门的贡献查询。
- 明确跨账户转账与跨月退款的筛选归属：账户查找定位该账户流水，退款原消费作为关系证据；商户查找与原消费归类不是同一个集合。
- 延续用户隔离、稳定分页、明确容量边界；不开放自然语言 SQL。涉及可重读证据的结果沿用 R1 的账本与计算版本契约，新增匹配语义纳入对应规则版本管理。

门槛：条件可解释，找到的流水可定位；遗漏、不支持和歧义有明确反馈。先测量实际查询计划与延迟，再决定是否增加索引或优化分页。

## R4：同口径消费比较

用户例子：“九月比八月多花的钱，主要在哪些分类？”

- 服务端在同一快照中读取两个期间，用共享贡献规则计算分类差额及消费/退款分解，模型只组织说明。
- 两个期间使用相同计算版本；跨发布重读证据时双版本校验不一致即要求重新比较。固定夹具独立核算双方金额和差额，不只比较两个共用算法的 API。
- 默认同币种比较，显示双方导入范围。未结束月份可选择截至同日比较，短月份明确实际日期，不自动年化或外推。
- 变化只能说明已导入数据的差异；不能把缺失账单解释成节省，也不能把金额相关性当成生活习惯的原因。
- 大额贡献可下钻到证据。暂不做商户实体合并、预测和“建议削减多少”。

门槛：分类差额之和等于总体差额，每个主要变化都有证据；不同覆盖范围的提示在结果旁可见。

R4 依赖 R1 的共享消费证据；比较结果沿用 R2 的会话与历史结果管理。

## R5：待办状态与订阅

总览 `NextActions` 提供预算提醒、即将到期、待核对及关联需重核的固定支出入口。R5 在该入口上增加持久化状态与订阅偏好，事件处理由 R7 交付。

用户新增能做：“这项我看过了；下次再处理；这一类以后不用提醒。”

复用现有总览入口和业务事实，新增已读、暂后处理及类型关闭状态。按用户、业务对象、期次和事件类型建立稳定身份，重复刷新不创建新待办；业务是否已处理继续来自预算/周期事实，点击已读不等于完成核对。

暂后状态到期后重新可见，关闭类型在后续读取与事件处理中均生效；用户可恢复类型订阅。到期无匹配仍只表示待核对。撤销流水、解除关联或撤回未发生确认时重新评估事实：已处理事项重新待核对时形成一次明确的新状态变化，不能被旧已读状态永久隐藏，也不能每次刷新重复提醒。

R5 依赖当前预算/周期能力与 R0 的持久化验收。验收覆盖已读、暂后和关闭偏好的跨刷新及登录恢复；已读不改变业务完成状态，撤回后可重新待核对。将重复读取、状态竞争、撤回重开及恢复准备加入固定回归。

## R6：固定支出候选发现

用户例子：“帮我找出可能每月都在扣的订阅。”

- 首版只识别月付：按同账户、币种、规范化商户及日期/金额模式形成候选。至少三个不同月份的观测作为起始规则，阈值经样本评估后确定。
- 每个候选显示形成依据、实际扣款月份、金额波动和已知缺口。数据不足返回“证据不足”，不推断已停扣或漏扣。
- 用户可以忽略、修改后创建、关联到已有项目。候选不得自动创建计划，也不自动关联历史期次。
- 确认建项使用独立提案，显示完整参数和来源证据；重复确认幂等。已有项目、暂停项目和已忽略候选参与重复检查。
- 模型可以解释候选，但确定性规则负责候选证据及约束，不引入独立训练服务。

先准备人工标注的独立样本；指标定义为候选精确率 `正确候选数 / 所有提出候选数`，目标至少 90%，同时报告正确候选、误报、漏报、召回率和样本覆盖。无候选时精确率不可计算，不能记作 100%。调节阈值的样本与最终评估样本分开，报告各类失败而不只报总分。这个数是待验证目标，不能以少量合成样本包装成真实准确率。

无重复建项是确定性硬门槛，使用可重复的确认/重试/并发脚本验证。真实样本不足时可以完成规则与交互实现、合成验收，但默认不启用自动发现，并保留真实样本验收缺项；其他阶段继续推进。

年付识别、金额预测和自动确认另行评估，不与月付发现一起交付。

## R7：事件与通知

基于 R5 的站内状态，为需要后台处理的事件添加事务内记录和幂等消费；业务事务回滚不产生有效事件，重试不重复生成有效通知。数据库恢复后保留关闭偏好并抑制旧事件重放，只有新状态变化触发后续处理。

接入 R6 的自动发现候选事件；会话查询变化订阅使用 R2 的持久会话，不将全局修订号变化广播成每条查询的提醒。

只有站内待办确实被使用，且用户明确需要离站提醒时，才追加一个外部渠道。届时单独交付时区/安静时段、用户订阅、退订、重试与投递回执；默认消息不含敏感交易详情。不同时接入邮件、短信和多个 IM。

门槛：同一事件无重复有效待办，事务回滚不发通知，关闭后不再投递。将事件竞争、恢复准备与投递重试加入固定回归。外部渠道未启用时，明确交付范围仅为站内状态与事件处理。

## 架构演进约束

| 能力 | 演进方向 | 明确避免 |
| --- | --- | --- |
| 账务计算 | 从预算抽出共享消费贡献计算，服务端统一口径 | 助手、报表、预算各写一套算法 |
| 查询证据 | 统一消费引用，账本修订号与计算版本共同拒绝混用 | 只靠模型工具选择或把修订号当完整账本历史 |
| 助手写入 | 每种操作独立校验，提案、显式确认、幂等回执 | 提前构建通用万能动作平台 |
| 持久任务 | 延续 PostgreSQL 持久状态、租约和领取令牌模式 | 未测量就引入 Redis、队列或服务拆分 |
| 模型质量 | 固定场景集加真实失败案例，分开记录工具正确性和文字质量 | 仅看回答流畅度或单一通过率 |
| 业务回归 | 仓库内合成夹具、独立预期、隔离库脚本及 CI；真实模型另行记录 | 缺少独立金额断言或无法重复运行的验收 |
| 性能 | 分离数据库查询、模型等待和浏览器渲染耗时 | 把长模型等待归因于数据库，盲目加缓存 |

是否采用 LangGraph 的更多能力取决于任务是否真的需要持久恢复与分支；不以图节点数、多 Agent 或工具数衡量进展。

## 执行顺序与完成门槛

执行顺序：**R0 → R1 → R2 → R3 → R4 → R5 → R6 → R7**。先形成证据闭环并保证连续使用，再扩展查询、比较、待办管理和自动发现。R6 若缺真实样本，完成可执行部分后记录验收阻塞，继续其他已具备条件的工作。R7 的站内事件可以完成，外部投递仍以渠道与订阅需求明确为进入条件。

每轮由 Codex 完成详细设计、代码实现、固定回归、必要的真实模型/浏览器验收及问题修复，再整理交付记录。交付记录必须分别列出代码完成、验收通过、外部条件缺失、提交状态和发布状态；不能用“代码写完”代替验收或发布。规则与共享计算修改必须更新版本并重跑受影响回归。

业务接口变化需完成契约回归，存储变化需完成迁移与恢复验证。真实样本认证和生产链路存在缺项时，交付记录保持对应未验收状态。

如果一个功能不能减少用户查账步骤、减少误判或帮助持续完成核对，应缩小或取消。公开多用户产品、共享账本、银行直连、资金操作、投资推荐和移动端原生应用不进入这条路线。
