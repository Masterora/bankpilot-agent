# R6 固定支出候选发现设计

状态：2026-09-29 已实现只读发现及发现决策的本地代码，服务端默认关闭；本轮验证与缺项见 [R6 决策记录](R6_DECISIONS_ACCEPTANCE.md)。R5 补验清单尚未完整执行，提案确认、助手入口及 R6 完整验收也尚未实现。识别阈值未经独立真实样本评估，不得把当前候选当成已认证订阅或发布精度。现有能力与限制见 [当前状态](CURRENT_STATE.md)。

只读切片的本地验证：`make verify` 与 `git diff --check` 通过；隔离 PostgreSQL 以合成流水核对连续三个月候选、窗口外到账退款、双用户隔离、已有计划归类、计划变化后的旧分页令牌拒绝，以及 10,000 笔成功、10,001 笔拒绝和大组最多展示 12 笔。修复复核另以隔离 PostgreSQL 与替代认证的 ASGI 路由验证默认关闭、显式启用、逐笔退款排除、全组退款及关系变化后的旧令牌拒绝；受控 Chromium 响应验证切换月份后旧分页不会写回。替代认证与浏览器桩不代表真实登录和完整端到端链路。完整关系与浏览器矩阵、真实样本精确率/召回率认证仍缺失。当前页面只允许用户主动读取和定位证据，不提供忽略、关联或确认创建。

## 目标与权限

用户希望从已导入流水中找到可能每月扣款的项目，查看每笔依据，再选择忽略、关联到已有固定支出或修改参数后创建新项目。发现结果是候选，不是已确认的订阅、漏扣或未来扣款预测。

账户归属、关系排除、金额、候选成员、重复检查和创建写入均由确定性服务端代码决定。模型最多选择只读发现工具并解释候选数量；候选证据由浏览器直接读取，不让模型决定候选成立、参数或确认结果。没有模型时，固定支出页面仍可完成整个流程。

首版只识别月付。年付、多个金额档位的同商户自动拆分、商户别名学习、自动建项、历史期次自动关联、离站通知及扣款预测不在 R6 范围内。

## 用户闭环

1. 用户从固定支出页打开“发现可能的月付项目”，选择截止月份；默认截止为 Asia/Shanghai 的上一个完整自然月。读取最近 12 个完整自然月的导入流水。
2. 页面分别显示可核对候选、证据不足或不明确的组、已忽略及已关联的组，以及读取覆盖和容量错误。无结果只说明当前规则未发现候选。
3. 每个候选显示账户、币种、原始商户文本、规范化依据、实际扣款日期和金额、最近观测、金额波动、观察窗口及已知覆盖缺口。逐笔可定位到账本；不显示“应扣未扣”。
4. 用户可以忽略候选，或选择一个归属自己的已有计划作“已由此项目管理”的关联。该关联只处理发现列表，不修改 `recurring_matches`，也不把历史流水标记为已核对。
5. 用户选择新建时，先看到预填但可编辑的名称、商户、账户、币种、预期金额、月付与首次日期。首次日期默认取当前业务日之后、能保留观测锚点日的最近日期；若最近月份没有该日，就顺延到有该日的月份并提示可能跳过一期，用户须显式核对。现有计划只从 `start_date` 推算，不能以短月月末作起点后仍声称保留原 31 日锚点。首次日期不能早于确认日；历史观测日期只作为证据，不用作计划起点。服务端生成含完整参数和来源证据的独立提案；用户再次确认才创建计划。创建成功后进入现有固定支出页，后续逐期关联仍由用户完成。

## 发现输入与规则

### 证据范围

- 查询必须绑定认证用户；同一可重复读快照中读取 12 个完整月、账户、确认关系、已有计划及发现决策。最多读取 10,001 笔以判定 10,000 笔容量；超限返回明确错误，不用前 10,000 笔推断“无候选”或精确率。
- 仅纳入负金额、有效账户、同一币种的实际导入流水。已确认重复关系的副本与本人转账双边按现有 `planning_evidence.excluded_ids` 排除；已关联固定支出期次的流水仍可作为证据，但其候选应归为“已有项目”而非重复创建。对窗口内扣款 ID 查询全部已确认退款关系，包括退款到账日在窗口外的关系；有任一退款关系的原扣款不计作有效观测，并显示“该笔存在已确认退款，未参与识别”。R6 不区分部分/全额退款，也不新增净额算法。关系读取失败或超限时整次发现不可用，不能把退款当作未发生。
- 账单来源、批次和行号只用于追溯。导入有空月、失败批次或未知覆盖时，标为“未观察到/覆盖未认证”；不得把空月说成未扣款。当前不持久化“账单已完整导入”断言。

### 规范化与成组

- 候选组键由 `user_id + account_id + currency + normalized_merchant` 唯一确定。商户规范化使用独立于识别规则的 `merchant_normalization_version`：当前规则为 Unicode NFKC、去首尾空白、内部空白折叠、大小写折叠；保留数字、标点和平台后缀，不凭模糊相似度合并不同商户。空值、只有支付平台通用名称或规范化后无可识别商户的记录不给出候选，报告原因。只读发现接口和持久决策均返回或保存该版本；实现持久化前先为当前规则固定一个明确版本值。
- 同组每个自然月只能有一笔可用扣款；若同月多笔、不同价格档位或可疑拆分无法唯一归属，标为“不明确”，不自动挑一笔。不同账户或币种永不合并。组键不包含价格、观察月份或识别规则版本，以便新账单到来后忽略/关联决定保持归属；规范化版本变化前必须先关闭发现入口，再以新迁移为旧决策逐条映射新组键并处理碰撞。不能确定一对一映射时保持入口关闭并停止该版本升级，另行设计人工核对流程；任何保存版本与运行版本不一致的读取或写入必须明确失败，不得让旧决策静默失效或误命中新组。
- 初始保守规则：最近 12 个完整月内，最近 3 个有效观测必须分属连续 3 个自然月，且最后一笔位于截止月或其前一月。以这 3 笔的账单日作为锚点，月末按现有 `due_in_month` 截短；窗口内其他观测日期相对锚点不超过 3 天。金额使用 `Decimal` 比较，所有有效观测相对中位数的偏差不超过 10%；不跨币种换算。不满足条件只返回证据不足或不明确，绝不推断已停扣。
- 这些 3 个月、3 天、10% 和最近 2 个月是待标注样本校准的规则初值，不是已验证精度。规则版本记录在响应和提案中；调整阈值必须升规则版本并重跑独立评估，不通过运行时环境变量静默改变候选含义。

候选按最近观测日期降序、组键升序稳定排序；每组返回最多 12 条本窗口观测。组键在服务端按上述四元组做 SHA-256，客户端只当不透明 ID 使用。响应包含完整窗口的观测数、被排除原因计数、查询账本修订号、发现规则版本、商户规范化版本和 `evidence_digest`。摘要覆盖成员交易 ID、日期、原始金额、确认关系、组键及规则版本；不把展示名称或模型文字当作证据版本。列表另返回 `discovery_snapshot_token`：在同一快照内由账本修订号、规则版本、规范化版本、候选排序与归类、相关计划及其配置/逐期匹配、发现决策及版本生成。每页重新计算完整结果并校验令牌；任何可见结果变化都拒绝旧页码，不仅检查账本修订号。

## 决策、提案与并发

### 发现决策

新增 `recurring_discovery_decisions`，按用户和稳定组键唯一保存 `active | ignored | linked | created`、目标计划 ID、单调版本、`merchant_normalization_version`、最小组身份及时间。无记录等价于 `active`、版本 0；恢复忽略或解除关联时保留 `active` 行并推进版本。`linked` 表示用户选择已有计划，`created` 表示通过本发现提案新建，两者都必须保存目标计划 ID；`active/ignored` 不得保存目标计划 ID。忽略后默认隐藏，用户可在“已忽略”视图恢复；关联只隐藏重复推荐，不写入逐期匹配。目标计划必须属于同一用户，且其在候选最近观测月份生效的配置与候选账户、币种一致；结束和暂停计划仍参与重复检查。商户或账户后续修改若使关联不再符合当前组键，列表提示“需重新核对”，不能悄悄重指向另一计划。

忽略、恢复、关联、解除均携带期望决策版本与客户端 `operation_id`。`recurring_discovery_operations` 按用户与操作 ID 唯一保存请求摘要和冻结回执：同 key 同请求只回放，同 key 不同内容返回 409。先锁用户、重读当前组和目标计划，再写决策与回执；数据库错误整体回滚。读取不创建决策或回执。客户端在发送前持久化不含流水正文的原请求，结果不明时只允许原 key/原载荷重试。

### 新建提案

`POST /api/v1/recurring/discovery/proposals` 接收客户端 `proposal_request_id`、组键、`evidence_digest` 与不含计划 ID 的 `RecurringDiscoveryDraft`（名称、商户、账户、币种、金额、固定为月付的周期及首次日期）。首次日期必须晚于当前 Asia/Shanghai 业务日；账户和币种须等于候选证据。服务端生成并冻结提案 ID 与计划 ID，随后用冻结计划 ID 组装现有 `RecurringInput`，复用现有创建服务的账户/币种校验及幂等身份规则。返回 15 分钟到期时间、原样参数、最多 12 条来源交易 ID/日期/金额及创建后不会自动关联历史期次的说明。提案仅保存最小证据引用和摘要，不复制原始描述或账单正文。同用户、同 `proposal_request_id`、同请求摘要回放同一提案；同 key 异载荷返回 409，创建请求响应丢失时可原样重试，不生成第二个提案。

`POST /api/v1/recurring/discovery/proposals/{id}/confirm` 仅接收提案 ID；先锁用户，再锁归属提案。已确认提案返回首次冻结的计划 ID，不再次创建。未确认时按最新账本修订、规则版本、候选组、证据摘要和目标账户重算并校验；任何变化返回明确失效冲突，用户需重读后重新生成提案，不自动沿用旧参数。

创建前检查同账户、同币种、规范化商户的全部已有计划（含暂停、结束及历史/未来配置），以及同组已忽略或关联决定。已有计划时返回冲突与可打开的已有计划 ID；用户须显式选择关联或另走现有手工创建流程。服务端在同一用户锁事务中创建 `recurring_plans`、标记提案已确认、保存冻结回执并将该组决策写为 `created`；不生成 `recurring_matches`。确认时再次校验冻结首次日期仍晚于当前业务日；过期则要求重做提案，不把已过去的日期作为新计划起点。确认失败不得留下部分计划、决策或回执。

`recurring_discovery_proposals` 保存用户、`proposal_request_id` 与请求摘要、候选组键、规则/账本版本、证据摘要、完整确认参数、服务端固定计划 ID、有效期、状态和冻结回执。已确认回执保留至用户删除，保证长期重试不重复建项；未确认到期提案保留可判定的过期状态，后续清理策略须保持旧 ID 不可重新执行。三张新表都使用用户外键级联、用户范围唯一键和必要索引；提案的 `id` 与固定计划 ID 全局唯一。备份、恢复、用户级联清理和表容量观测纳入迁移验收。

## 接口与错误契约

- `GET /api/v1/recurring/discovery?through=YYYY-MM-01&offset=0`：`through` 必须是完整月的月首；每页最多 20 组，返回窗口、账本/规则版本、商户规范化版本、`discovery_snapshot_token`、覆盖说明、当前有效组的有界列表和各类总数。规则分类与用户决策为两个字段；默认只列 `active` 组，`ignored/linked` 不混入当前候选。下一页请求须携带首次读取的 `discovery_snapshot_token`；服务端重算完整结果，令牌变化返回 409 并从第一页重读。分页必须在完整分组与排序后执行，不能只扫描第一页；超限直接 422。
- `GET /api/v1/recurring/discovery/decisions?status=ignored|linked&offset=0`：只从当前用户保存的决定读取历史，每页最多 20 条，按更新时间降序、组键升序排列；返回最小组身份、规范化版本、状态、版本、目标计划 ID、`evidence_status` 和 `decision_snapshot_token`。该列表不扫描交易，不受发现的 10,000 笔容量限制；默认 `evidence_status=not_checked`，只有一次成功的当前窗口证据核对才可标记 `present` 或 `missing`，容量错误时不得声称“没有证据”。翻页令牌覆盖本用户决定及版本，变化后返回 409。
- `GET /api/v1/recurring/discovery/decisions/{group_key}/evidence?through=YYYY-MM-01`：按当前用户已保存的决定查回组身份，再使用同一完整发现快照规则核对该组；成功时返回 `present` 或 `missing`，超限时返回 422 且历史决定仍可独立查看和撤销。不为不存在或其他用户的组泄露证据。
- `POST /api/v1/recurring/discovery/decisions`：忽略、恢复、关联、解除；均携带组键、期望决策版本和 `operation_id`；首次忽略或关联还须携带截止月份、`evidence_digest` 与 `discovery_snapshot_token`，关联另须携带目标计划 ID。成功和同 key 回放均返回同一冻结回执：操作 ID、组键、新状态、新版本、目标计划 ID（如有）和最小组身份。
- `POST /api/v1/recurring/discovery/proposals`：携带 `proposal_request_id`，冻结候选证据及无计划 ID 的完整草稿；返回完整可复核提案，不直接写计划。
- `POST /api/v1/recurring/discovery/proposals/{id}/confirm`：确认或回放冻结创建结果。提案只可由所属用户读取/确认。
- `GET /api/v1/recurring/discovery/proposals/{id}`：按用户读取原样冻结提案、状态和回执，供刷新及结果不明时查回；未知 ID 和其他用户 ID 均返回 404。

除只返回 `enabled` 的认证可用性接口外，所有发现读取与写入均受同一个服务端默认关闭开关约束。关闭时不读取或修改发现决策与回执；重新启用后，原操作 ID 仍按原样回放。

统一 `{detail:{code,message}}`：`discovery_capacity` 为 422；`discovery_evidence_stale`（含计划或决定改变后的旧快照）、`discovery_decision_conflict`（版本或非法状态转换）、`discovery_duplicate_plan`、`discovery_operation_conflict` 为 409；`discovery_proposal_expired` 为 409；不存在或不属于当前用户返回不泄露归属的 404，发现开关关闭时返回 404 `discovery_unavailable`，依赖不可用为 503。错误不回显其他用户的商户、交易或计划。网络结果不明时页面保留原提案 ID/`proposal_request_id`/操作 ID；提案创建用原请求 ID 重试，确认先按提案 ID 查回或原样重试，不生成新确认。

## 界面与助手

固定支出页增加“发现可能的月付项目”入口和独立抽屉；不混入现有逐期交易候选列表。卡片先给出实际观测与范围，再给动作。证据不足、不明确、已有项目、已忽略和读取失败有不同状态；切换月份或账号时旧响应不能覆盖新视图。编辑提案沿用当前固定支出表单字段，但确认页独立展示冻结参数和证据；金额始终由服务端 Decimal 字符串提供。

助手只增加一个只读发现工具，返回有界候选数量、规则版本、覆盖状态与打开固定支出发现视图的目标；逐笔证据不发送模型。新增工具须升级助手协议/结果版本并拒绝旧客户端把新结果当旧结构解析。模型回复不能替代页面证据或确认。真实模型能否正确选择工具、解释“可能”与“证据不足”另行验收；失败时用户仍能从页面完成流程。

## 实施顺序与验收

先按 [R5 补验清单](R5_ACCEPTANCE.md#进入-r6-决策切片前的补验清单)逐项完成容量、竞争、恢复和浏览器复核，再进入 R6 决策写入。R6 按一个可运行闭环交付：确定性识别与只读页面 → 决策持久化 → 提案确认与现有计划联动 → 助手只读入口。每步以真实接口和隔离 PostgreSQL 验证后进入下一步；不以静态检查代替业务或浏览器验收。

### 下一迭代：发现决策持久化

**目标与边界。** 在当前服务端默认关闭的只读发现上，交付忽略、恢复、关联已有计划、解除关联的完整读写闭环。用户刷新或重新登录后仍能查看和撤销自己的决定。本轮不创建计划、不修改 `recurring_matches` 或账本金额、不增加模型工具，也不扩大一般用户启用范围。开始实现前按 [R5 补验清单](R5_ACCEPTANCE.md#进入-r6-决策切片前的补验清单) 逐项验证并记录结果；这个进入门槛不等于 R6 识别质量认证。

**数据与接口。** 新增 `recurring_discovery_decisions` 和 `recurring_discovery_operations`，使用新的 Alembic 迁移并更新结构版本，不改写已发布迁移。决策按 `(user_id, group_key)` 唯一保存状态、目标计划、单调版本、`merchant_normalization_version`，以及账户、币种和规范化商户的最小组身份；无记录投影为 `active`、版本 0。表结构预留 `created` 状态，本轮接口不能设置它。操作按 `(user_id, operation_id)` 唯一保存请求摘要和不含原始流水正文的冻结回执。当前发现列表返回规则分类及独立的用户决策字段，默认只显示 `active`；已忽略和已关联视图使用单独的已保存决策查询，即使当前窗口超限或原流水被撤销也可读取并撤销决定。未完成证据重读时显示“证据未核对”，通过单组核对接口成功读取后才区分有证据与无证据。当前发现令牌覆盖所有决定及版本；历史决定列表令牌覆盖所有决定和其目标计划的可见配置与状态，变化后旧页均返回 409。所有读取均不创建决策或回执。

**动作与写入规则。** 唯一合法的首次转换为 `active → ignored`（忽略）或 `active → linked`（关联）；撤销仅允许 `ignored → active`（恢复）或 `linked → active`（解除）。跨状态直接改写、同状态使用新 key 重做，以及对预留的 `created` 状态执行本轮动作均返回 409；同 key 同载荷始终回放原冻结回执。首次忽略或关联携带 `operation_id`、组键、截止月份、当前 `evidence_digest`、`discovery_snapshot_token` 和期望决策版本；关联还须携带目标计划 ID。恢复或解除只携带操作 ID、组键和期望决策版本，允许当前证据消失。请求摘要覆盖所有提交字段，禁止把同 key 用于不同动作。服务端先确认发现开关已开启，关闭时连回放也返回 404 且不读写决策；开启后先锁用户，再查同 key 回执。首次忽略或关联须重算当前组和完整发现快照，核对令牌、证据、决策版本及目标计划归属；恢复或解除只按已保存决定及版本核对，不依赖交易扫描。校验通过后在同一事务中写决策及回执。首次忽略或关联要求当前组有可识别商户与有效扣款；同账户、同币种及最近观测月份的目标计划配置须匹配，暂停或结束计划仍可作为已有项目核对。目标计划在查看后有任何配置或状态变化，旧快照必须拒绝；后续配置不再匹配时标记“需重新核对”，不自动重指向。关联只管理发现结果，不生成历史期次匹配。客户端发送前在当前用户的 sessionStorage 冻结不含流水正文的原请求；存储失败不得发送，结果不明时只能用原 key、原载荷重试，成功后清除。

**验收出口。** 隔离 PostgreSQL 与真实 ASGI 路由验证开关关闭时可用性返回 `enabled=false`，其余发现 GET/POST 均拒绝且数据库不变；覆盖双用户隔离、四种合法转换和全部非法转换、跨刷新保留、版本单调、同 key 回放与异载荷 409、并发写入仅一条有效决定、回滚无半成品、计划归属与配置冲突、证据或计划变化后拒绝旧写入及旧分页令牌；确认 `recurring_matches`、计划和账本金额未被修改。测试历史列表在原流水撤销和当前窗口超限时仍能读取与撤销决定，未核对证据时不声称“无证据”；商户规范化版本变化模拟必须阻止旧决定静默作用于新组。迁移在隔离库执行升级、检查、降级再升级及备份还原回执校验，不在共享库降级。浏览器覆盖中英文、375px/1440px、键盘、刷新恢复及弱网结果不明重试；`make verify` 和差异检查另行记录。缺少任何一项只报告未验收，不据此开启默认开关。

确定性硬门槛：双用户隔离；同账户/币种限定；重复、转账、已关联及窗口外到账退款的关系处理；10,000/10,001 容量边界；空月不推断漏扣；同月多笔与同商户多档位不误建；忽略/关联/恢复/解除跨刷新保留且版本单调；暂停/结束/忽略组参与重复检查；同 key 回放与异载荷冲突；创建提案响应丢失后原请求 ID 只得到同一提案；并发确认最多一个计划；账本修改和撤销导入后旧提案失效；计划或决策在翻页间变化时旧快照令牌被拒绝；回滚不留半成品；备份还原后回执仍可回放。用历史三个月扣款在今天确认建项，必须只从未来首次日期生成期次，历史月份不产生新的待核对/提醒。浏览器覆盖中文/英文、375px/1440px、键盘、刷新恢复、弱网及结果不明重试。`make verify`、隔离迁移往返和 `git diff --check` 分别记录。

模型质量单独记录工具选择、参数提取、错误解释与无数据措辞。真实模型调用需明确配置及外部用量授权；没有这项记录不得声称自然语言发现已验收。

## 样本评估与启用门槛

在编码阈值最终值之前，收集经用户授权、脱敏且来源认证的真实账单窗口，人工标注候选组、实际同一月付项目、同商户多订阅、退款、缺月和已有计划。按用户/商户分割调参集与最终盲测集，不能让同一组交易跨集泄漏。盲测集至少包含 50 个真实月付组及 50 个非月付或易混淆组，覆盖至少两个来源格式，并记录不同账户、币种、商户和历史长度的分布；样本不足则不达到一般用户启用门槛。保留逐例判断、规则版本、脱敏证据 ID、失败原因与复核者；合成样本只证明控制流。

盲测前冻结可评估范围：12 个完整月内，账户和币种已知、商户可识别、同组至少 3 个不同月份存在扣款；不要求连续、金额稳定或同月只有一笔，这些必须由规则决定，不能从召回分母中事后排除。对该范围内所有人工标注的真实月付组计算召回率；“证据不足”“不明确”及被规则拒绝的真月付都计为漏报。样本覆盖率为该范围内真月付组数 / 盲测集全部真月付组数，反映首版规则在真实资料中可能服务的比例。

最终评估分别报告正确候选、误报、漏报、精确率、召回率、样本覆盖率、拒绝/不明确数量以及按来源和币种的分层结果。一般用户启用须同时满足：候选精确率至少 90%（分母为所有提出的候选）、上述固定范围内召回率至少 50%、样本覆盖率至少 60%，且确定性硬门槛全部通过。无候选时精确率不可计算，不能记 100%；任一分层样本不足须明确标为未认证，不用总体结果代替。报告样本量与置信区间，不把这些点估计称为总体准确率。阈值如需调整，只能在查看盲测结果前基于调参集修改并升规则版本；盲测后不以同一批样本反复调到通过。真实样本不足或任一门槛未达标时，规则和交互可以以受控方式完成合成验收，但默认不向一般用户开启自动发现，也不把 R6 记为已发布。

## 待落实的实施决策

样本标注后固定商户通用名称清单及金额/日期阈值；在迁移前核对提案及回执的长期保留成本和备份结构版本。上述参数在设计中有保守初值，但未经独立样本评估不宣称识别质量。
