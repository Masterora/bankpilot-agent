# R2：会话与操作结果恢复

规划日期：2026-09-21。代码基线：`main@c183b5b`。状态：待实现。由 Codex 负责设计落地、实现、验证、评审和交付记录，不按时间或 A/B 阶段拆分。

## 目标与完成标准

用户刷新页面、重新登录或隔天回来后，可以找到上次对话、查看当时的消费结果、核对预算操作状态，并继续查询当前账本。

完整路径：**打开历史会话 → 恢复消息与选中范围 → 区分历史和当前结果 → 继续提问或明确确认提案 → 刷新核对结果。**

本轮以“已受理的问题可找回、预算操作结果可核对、查询范围明确可继续”为唯一主线。交付必须同时满足：已受理消息不因刷新丢失；历史金额不被静默替换；重复发送不重复生成提案；恢复页面不触发预算写入；其他用户无法读取或操作该会话。

## 本轮范围

| 能力 | 交付行为 |
| --- | --- |
| 会话管理 | 新建、分页列表、打开、删除；标题取首条问题的截断文本，不增加模型调用 |
| 消息保存 | 保存用户问题、助手答案、服务端结构化结果、查询范围、生成时间和版本 |
| 中断恢复 | 刷新后显示处理中、完成或失败；通过请求标识查询结果，禁止自动重新发送 |
| 历史证据 | 汇总保留当时数值；明细沿用 R1 双版本校验，失效时明确要求新查询 |
| 提案恢复 | 读取现有提案真实状态、有效期与冻结回执，用户明确确认后才可能写入 |
| 继续对话 | 服务端构建受限上下文，当前事实重新查询；选中的月份、分类、币种可恢复 |
| 删除与容量 | 主动删除会话及消息、设置可配置容量上限，并提供可执行的恢复降级方案 |

不增加助手写操作种类，不实现任意流水搜索、跨期比较、自动周期识别、通知、完整逐笔历史快照、附件、自动删除历史、历史搜索/分组/归档或跨设备实时同步。账本、预算与固定支出的现有业务规则保持不变。

## 页面行为

- 沿用现有深色助手面板，在面板中增加“新对话”和可收起的历史列表，不增加独立聊天主页面。窄屏仍在同一助手内切换列表与详情。
- “新对话”仅打开空白输入区，首次发送时才原子创建会话与首个轮次，空会话不保存。标题取首次受理问题的截断文本。
- 打开助手优先恢复当前标签页最近访问的有效会话；重新登录或本地标识不存在时恢复服务端记录的最近访问会话，无可访问会话则显示空白输入区。打开历史不调用模型；不同标签页不强制同步当前会话。
- 列表每页 20 条，按创建时间与 ID 倒序稳定分页，另显示最后活动时间，活动更新不改变已加载列表排序；会话内每页 20 个完整轮次，按序号加载更早内容。
- 每次首次发送、继续提问与重新查询都显示明确的月份、分类和币种范围；新问题产生的范围变化在结果旁展示。达到轮次上限时提供“新对话继续”，仅继承用户确认的结构化范围，不复制旧金额、旧请求或待确认提案。
- 已保存结果显示“当时结果”和生成时间。刷新历史页面不自动调用模型；“重新查询”追加新消息和结果，旧结果仍保留。
- 明细版本一致时可继续展开；账本或计算版本不同则隐藏明细并提示“账本或规则已变化，请重新查询”。预算额度和固定支出状态也不能仅凭账本版本认定为当前状态。
- 待确认提案展示服务端计算的当前可执行状态，不直接把数据库中的 `pending` 显示为可确认。恢复时不延长现有 15 分钟有效期；已确认展示当时回执，取消、过期、冲突或会话失效时隐藏确认入口。
- 发送中刷新后显示请求状态；失败保留问题，可明确重试。切换会话、用户退出或快速翻页时，迟到响应不能写入另一个会话。
- 删除需要明确确认，提示“删除对话不会撤销已经执行的预算修改”。未发送草稿仅留页面内存，不上传或作为模型历史。

## 持久化与请求契约

沿用 FastAPI、Pydantic、SQLAlchemy 和 PostgreSQL。新增会话与轮次记录，复用现有助手提案表；不引入 Redis、消息队列、通用会话框架或独立服务。

- 会话保存用户归属、标题、创建/活动时间和已选查询范围。每次查询均按认证用户限定归属，客户端传入的会话 ID 不构成权限。
- 轮次保存问题、请求标识、输入摘要、递增序号、处理状态、结构化回复、提案引用和时间。以 `(会话 ID, 请求标识)` 唯一约束防重，同标识不同内容返回冲突。
- 同一会话只允许一个处理中轮次，多标签页并发请求返回明确冲突；不同会话可独立处理。序号由服务端分配，分页排序不依赖可碰撞的时间戳。
- 客户端仅提交新问题、请求标识及明确选中的范围；历史角色、答案、工具结果和操作回执均从服务端读取，禁止客户端伪造助手消息进入历史。
- 模型等待不持有数据库事务。请求先提交处理中记录，完成时在短事务内保存结果；提案创建与结果关联原子提交，避免网络中断产生无法恢复的孤立提案。
- 保留当前 90 秒对话预算。处理中记录提交时按数据库时间确定截止时间，保存唯一完成令牌，不因轮询、重试或重启续期。状态只允许 `processing → completed/failed`，终态不可重新进入处理中。
- 同标识重试返回原处理中状态或已完成结果。失败后由用户明确重试，创建关联原轮次的新请求标识；网络结果不明时先查询原请求状态。
- 预算确认继续复用现有确定性校验与幂等回执，不另建写入流程。历史确认回执不得覆盖用户后续修改过的预算额度。

接口按现有 `/api/v1/assistant` 组织：会话列表/详情/删除、首次发送及轮次提交/状态读取、选中范围更新，以及原有提案确认/取消。读操作使用 GET、写操作沿用 POST；实现前固定请求与响应模型、分页字段和错误码。旧无会话聊天协议不得绕过持久化，前后端同批升级，旧客户端明确提示刷新。

### 中断收敛与完成写回

助手会话服务提供同一套过期收敛操作，由 API 启动时执行一次，并由受应用生命周期管理的后台任务每 15 秒批量执行。会话状态读取及新轮次提交前也调用该操作，避免后台扫描延迟持续阻塞用户。只处理截止时间已到的记录，不将其他实例仍在处理的请求判失败；不自动重新运行模型。

数据库正常可用时，过期记录在下一次扫描或请求访问时变为 `failed`，释放会话中的处理中占位。数据库不可用期间不承诺该时限，接口返回服务不可用；恢复连接后继续扫描。原请求遇到可捕获的模型错误或取消时立即尝试标记失败，写失败则由截止时间机制兜底。

成功写回必须在同一短事务中锁定会话并确认会话有效，再以 `status=processing`、完成令牌相同及数据库时间未到截止时间为条件更新轮次。零行更新意味着结果已失效：丢弃答案，不保存提案。提案创建、轮次完成和结果关联共同提交或共同回滚。截止扫描、删除、确认与完成写回的锁顺序在实现前固定，禁止边持锁边等待模型。

验收在“处理中记录已提交”“模型已返回、结果未提交”“结果已提交、响应未送达”三个位置注入中断，验证多实例扫描、迟到完成和重试均不能生成额外提案。

### 客户端恢复标识

发送流程明确区分三种状态：未发送草稿、提交结果未知、服务端已受理。只有服务端已保存轮次，页面才能显示“已保存”；网络中断不能显示为确定失败。

点击发送时，客户端先按认证用户 ID 将请求恢复记录写入当前标签页 `sessionStorage`，然后发送。记录包含请求 UUID、目标会话 ID（首次发送含创建 UUID）、原问题、语言、明确范围及协议版本，仅用于精确重试，不保存凭据、助手答案或证据明细。已发送问题可能包含财务信息，记录仅在当前标签页保留，确认服务端已受理后删除正文；未发送草稿仍只在内存中保存。退出、用户切换和确认删除会话时清理对应记录，迟到响应不得重新写入。

首次发送在服务端按用户与创建标识去重，会话创建、首个轮次和配额校验同事务提交。创建或发送响应丢失时，刷新后用原标识查询：已受理则恢复轮次；404 则显示“尚未确认接收”，提供“重新查询”和“重试本次发送”。明确重试必须使用保存的完整原输入与原标识，不能重新生成请求 ID；原请求之后到达也只对应同一个轮次。未知状态时不允许把编辑后的问题作为原请求重试。

恢复出的处理中轮次每 3 秒查询一次，面板隐藏时暂停，重新打开立即查回。终态后取得持久化结果，再清除待恢复标识。已失败轮次可由用户明确发起新请求，关联原轮次；完成轮次不自动重发。

同会话的重复标识返回原结果，同标识不同输入返回冲突；首次发送的重复标识返回原会话和首轮。删除后保留仅含用户、创建标识和删除状态的最小去重记录，不含问题或范围，不计入可见会话配额，也不重建会话；本轮不自动清理这类记录。

若浏览器存储不可用或写入失败，在发送前提示刷新前无法保证恢复未确认请求，保留页面内的原请求记录供重试，不宣称跨刷新恢复已具备。存储损坏或退出后本地记录清空时，从服务端历史找回已受理请求；未受理内容不保证保留。此限制纳入界面说明与验收，不允许静默绕过。

### 提案状态与执行资格

保留现有持久化状态 `pending/applied/cancelled`；读取接口另返回 `effective_status`、`can_confirm` 和不可执行原因。按以下顺序计算：

1. 已执行或已取消，返回对应终态；已执行仅显示冻结回执，不声明当前预算仍为该额度。
2. 待确认但所属会话已删除或不可访问，不提供确认能力；异用户统一按不存在处理。
3. 已到提案截止时间，返回 `expired`，即使原存储状态仍是 `pending`。
4. 目标预算 ID 或版本不符，返回 `conflict`。目标不存在的提案也须复查目标仍不存在。
5. 仅其余有效提案返回 `pending` 且 `can_confirm=true`。

状态读取不执行预算修改，不通过异常回滚假装保存过期终态。界面的可确认状态只代表读取时的检查结果，确认接口必须再次在事务内验证用户、会话有效性、提案期限及目标版本，并沿用既有预算写校验和冻结回执。确认与删除发生竞争时按同一锁顺序执行，不依赖页面按钮是否可见。

取消、过期或冲突后的再次修改必须由用户明确提出新请求，重新查询预算并生成新提案；恢复历史不能更改旧提案内容、延长期限或自动生成替代提案。上线前已存在、未关联会话的待确认提案统一失效；已完成回执保留，不伪造历史会话。

## 历史事实与模型边界

保存当时的汇总、覆盖信息、账本修订号、计算版本和显示所需结构，不复制完整交易明细。历史记录不代表可以重建任意时点账本。

日期和指代按以下规则解释，服务端保存本轮受理时的业务日期及最终明确的查询范围：

- 用户明确指定的日期、分类和币种优先；“本月”“上个月”按本轮首次受理时的业务日期和配置时区解释，不沿用历史消息日期。相同请求标识的重试保持首次受理语义。
- “这些退款”“这个分类”等指代只继承用户明确选中的证据范围；多个候选或上下文不足时先澄清，不默认选择最后出现的金额。
- 九月餐饮会话在十月问“本月呢”，保留明确的分类/币种，将月份切到十月；问“这些退款呢”仍指向所选九月证据；没有明确选中范围则澄清。
- 历史卡片的“重新查询”使用卡片中明确的历史月份、分类和币种查询当前账本，不按今天重新解释原问题。结果追加为新轮次，旧结果不变。

继续聊天最多发送最近 7 个完整成功轮次与本次问题，共不超过 15 条消息，并设置总字符上限；按完整轮次截断，不截断到孤立答案，不把失败轮次当作已有结论，也不自动生成模型摘要。结构化选中范围单独传递，早期历史仍供用户阅读；超出上下文后无法确定指代时明确要求用户选中结果或补充范围。

历史文本、商户和备注始终作为数据。服务端不从历史叙述推导授权、当前金额或提案状态；需要当前事实时必须重新运行受限查询。存储结构带版本，无法识别的历史结构只提供安全文本和不可重建提示，不按新结构猜测字段。

## 保留、删除与恢复

会话不按天数自动过期，由用户主动删除。每用户 100 个可见会话、每会话 200 个轮次作为集中配置的初始工程上限，不视为经使用数据验证的产品最佳值。问题长度沿用现有限制，结构化回复另设大小上限。达到会话上限提示主动删除；达到轮次上限提供“新对话继续”，不静默丢弃或覆盖已有内容。重试同一请求不重复占配额，新失败轮次仍计数，防止无限积累。

在线删除物理移除消息、上下文及标题，保留必要的无内容去重记录。已执行操作的冻结回执独立保留，不因删除聊天撤销预算或删除业务审计。删除确认提示待确认提案将失效、已执行预算不撤销、历史备份可能仍保留对话。

删除、轮次完成和提案确认按一致锁顺序校验：删除先提交则待确认提案取消、处理中轮次失效；确认先提交则保留已完成业务与回执，随后删除对话。保存下来的提案 ID 不能在删除后执行待确认操作。

新增表纳入备份、还原、结构核对与恢复准备。R2 不重写历史备份，不实现跨备份删除清单。备份保留周期由部署配置和 R0 管理，不承诺在线删除立即清除旧备份。

本轮交付明确的恢复降级路径：在隔离恢复库完成内容与结构核对后，由操作者确认“清除恢复库中的全部助手会话历史”再执行恢复准备。该操作清除所有恢复出的聊天内容而非猜测删除范围，取消待确认提案、使未完成轮次失效、清除认证会话；保留账本、预算、固定支出、月报及已执行操作回执。处理外键和去重身份后，旧客户端不能用恢复前的请求重新创建已清理会话。

恢复工具必须先展示目标数据库、待清理数量和保留的数据范围，要求明确的恢复库目标与清理确认，并记录结果；未完成清理及复核不得开放恢复环境。降级代价是未删除的聊天历史也无法继续使用，必须在运行手册和操作提示中说明。此方案不代表恢复后的账本比备份更新，RPO 仍按备份时间说明。

验收只在一次性隔离恢复库执行，验证清理重复执行安全、清理前后业务数据与已执行回执一致、旧请求拒绝以及无模型调用或预算重放。生产执行仍需单独授权。未来若必须保留恢复出的未删除对话，再在 R0 中实现独立删除记录与重放，不作为本轮依赖。

## 实施顺序与文件归属

1. 固定会话、轮次、提案关联及状态转换契约，编写迁移与隔离库验证。
2. 实现会话归属、配额、分页和删除；接入聊天持久化、请求去重与中断收敛。
3. 接入历史结果与提案恢复，验证删除、完成和确认之间的竞争。
4. 完成助手历史界面、继续查询、跨会话请求隔离与移动端交互。
5. 扩展固定回归、迁移恢复检查和浏览器验收，评审并修复问题后形成交付记录。

服务端会话持久化扩展现有助手仓储；模型规划与预算确认仍在助手服务中。会话生命周期有独立职责时增加会话服务，不按每个接口拆文件。前端保持在 `features/assistant`；仅将有独立状态的历史列表、消息展示或恢复 Hook 拆出，不为单个类型或一次性包装新增文件。

## 验收门槛

| 场景 | 必须满足 |
| --- | --- |
| 刷新、退出后重新登录 | 已受理消息、查询范围和真实操作状态恢复；未受理输入不冒充已保存；退出清除本地标识，无额外模型调用或写入 |
| 首次发送或响应丢失、重复提交、多标签页 | 空会话不保存；404 后可用保存的原输入明确重试，同一请求仅一轮和一份提案；同标识不同内容拒绝，删除不复活 |
