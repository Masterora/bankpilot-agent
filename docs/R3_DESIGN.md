# R3：受限流水查找

设计日期：2026-09-21。设计时基线：`main@7d569a5`。R3 已在 `063380a` 基线上完成本地实现；本文件保留设计取舍与验收目标，实际行为、通过项和缺项以 [交付记录](R3_ACCEPTANCE.md) 为准，未完成项不视为已交付。

## 目标

用户输入“九月某商户的 200 元扣款”，能够检查查询条件、找到流水、打开来源详情，并在返回助手后继续查找。手动筛选和助手查询使用同一服务端匹配规则。

本轮只完成“找到流水”这条路径。消费差额解释留给 R4；商户别名推断、模糊相似度、自然语言 SQL、跨年全库搜索和新增写操作不进入本轮。

## 改造前问题与取舍

改造前 `LedgerPage` 拉取期间内全部流水和核查记录，再在浏览器中按账户名称、分类、币种及商户/备注过滤；没有金额条件和服务端结果分页。`LocalBankingGateway` 提供其他业务共用的原始查询，不能为改造账本而改变其语义。

新增独立查找用例，账本改用分页查询，现有统计、核查和预算入口保持各自读取契约。复用分类装配与已确认关系，不另写一套消费计算。

首版采用“SQL 限定用户与日期等基础条件 → 有界完整读取 → 统一规范化与分类匹配 → 稳定分页”。这样避免数据库文本排序规则与 Python 规范化不一致，也避免分类规则在 SQL 中重复实现。候选超过 10,000 笔时拒绝并要求缩小范围，不对截断数据生成结果数量。索引和更复杂的 SQL 下推由实际查询计划决定。

## 用户路径与页面

### 账本

沿用现有账本、深色样式、流水详情和分类修改入口，不增加独立搜索页面。

- 默认显示日期、商户或备注输入框与“查询”。账户、币种、方向、金额、分类、来源批次放在“筛选”中；当前启用条件显示为可删除的标签。
- 条件草稿与已执行条件分离。编辑后按“查询”生效；旧结果仍绑定旧条件，不能被标成新条件结果。清除单个已启用标签立即重新查询并回到第一页。
- 日期默认沿用账本期间；账户按 ID 区分，不使用名称作为身份。支持同名不同币种账户。
- 结果显示“共 N 笔”、原始带符号金额、币种、商户、日期、账户和必要关系状态。没有原始流水金额合计卡，避免被理解为实际消费。
- 每页 20 笔，上一页/下一页；空结果隐藏分页。筛选错误保留输入，加载失败保留原条件并提供“重试”。
- “导出 CSV”导出当前已执行条件下的全部匹配流水，不只导出当前页；导出沿用查询版本，失败不生成部分文件。
- 点流水打开现有详情，来源文件/行号及退款原消费等具体证据按需展开。分类修改成功后使查找结果失效并重查，符合条件的集合可能随之变化。
- 显式查询条件写入 URL，支持刷新、前进和后退；不保存未提交草稿。商户文本属于个人数据，不写入请求日志或分析事件。退出和切换账号清理查找 URL 与本地状态。

### 助手

助手新增只读 `find_transactions` 工具。明确条件可直接执行，不为只读查询增加确认弹窗。

1. 问题明确时，模型产生严格结构化条件，服务端验证并执行。
2. 日期缺失时使用助手当前选中月份，结果条件中显示实际起止日期；“九月”使用选中参考年份。“最近”“差不多 200”“那个账户”等无法唯一确定的条件先追问，不能偷偷删除限制。
3. 账户名称有歧义时返回当前用户名下的候选名称及币种供选择。模型传入未知或其他用户账户 ID 均不能获得结果。
4. 答案下显示精简的结果卡：条件、笔数、首屏流水、“修改条件”和“在账本查看”。逐笔内容直接由服务端返回前端；模型只接收条件、数量、状态，不接收商户备注等逐笔载荷，也不编造流水说明。
5. “修改条件”在同一固定宽度助手面板中展开小表单，提交直接调用查询接口，不再次调用模型。查询成功后，通过独立会话上下文接口保存规范化条件；保存成功后才更新可续问的显式查找上下文，原历史卡不改写。查询结果暂存在当前面板，不产生伪造的助手轮次；保存失败保留结果并提示“条件未保存”，提供重试。
6. 在账本查看携带完整条件；打开一条流水使用按 ID 读取接口，不能为定位而加载整个期间。返回助手时恢复原页面筛选、页码及滚动位置。

助手宽度沿用 420px，上限为可用视口；表单、加载、错误、历史和空状态不改变宽度，输入区高度保持现有约束。中英文及 375px 窄屏同步验收。

## 查询规则

| 字段 | 首版语义 |
| --- | --- |
| 日期 | `start_date/end_date` 必填，按 booking_date 闭区间；允许范围与现有账本 `validPeriod` 一致，服务端最终校验；使用既有 UTC+08:00 业务日期规则 |
| 账户 | 可选单一 account_id；省略表示当前用户全部账户 |
| 币种 | 可选；存在金额限制时必须选定币种，多币种不能默认按人民币比较 |
| 方向 | all / debit / credit；负数为支出、正数为收入，零金额仅在 all 中出现 |
| 金额 | 对绝对值设置闭区间，Decimal 字符串、最多两位小数、非负、下限不超过上限；精确 200 表示 min=max=200.00，扣款再加 debit |
| 文本 | 一个最长 100 字符的字面子串；NFKC → casefold → 连续空白合并 → 首尾去空白，对输入与字段使用同一函数 |
| 文本范围 | merchant 或 merchant_or_note；手动框默认后者，“某商户”工具查询使用前者；不拆词、不进行拼音/别名/正则或通配符匹配 |
| 分类 | 可选单一现有分类，使用原分类规则与人工覆盖后的最终分类，不用退款原消费分类替代到账流水分类 |
| 来源批次 | 可选 import_batch_id，校验用户归属，保留现有导入下钻能力 |

“收入”在此仅指原始正数流水，不推断工资；退款按到账日期、到账账户、到账商户匹配，原消费只作为关系证据。确认重复和转账仍出现在原始流水查找中并带状态，不因其不计入实际消费而自动隐藏。

排序固定为 booking_date 降序、occurred_at 降序、transaction_id 升序。未知时间精度沿用原显示方式，不把补齐时间描述为真实交易时间。

容量统计的候选集合：已完成用户、日期、账户、币种、方向、金额和批次限定，但尚未应用文本及最终分类的集合。SQL 最多读取 10,001 笔用于判定上限；恰好 10,000 可继续。超过上限不返回部分结果、部分计数或“无匹配”。

## 服务端契约与一致性

计划新增 `POST /api/v1/transactions/search`，使用 JSON body 避免把商户文本放入服务端访问日志查询串。该接口只读、不创建搜索记录。

请求包含 `filters`、`offset`（20 的倍数）、可选 `expected_revision` 与 `expected_search_version`。第一页新查询省略版本；翻页、历史明细与原结果定位必须携带两个版本。版本必须同时出现，非零 offset 缺版本拒绝。

响应包含规范化 `filters`、`total_count`、`items`、`offset`、`has_more`、`ledger_revision`、`search_version`。每条只返回已有流水展示字段、account_id 和已确认关系状态；不混入模型推断字段。页数按完整匹配集合计算。

所有读取在同一可重复读事务中完成：认证、版本、候选、分类覆盖、关系及计数属于同一快照。翻页重新查询并核对版本；分类修正、导入撤销、关系修改等造成修订变化时返回 409，不能拼接不同版本页面。

新增 `search-v1` 匹配语义版本，覆盖规范化、分类依赖、匹配与排序规则；依赖分类规则发生变化必须同步升级。流水查找不计算消费，因此不伪用 spending-v1 作为查找版本；从流水转入实际消费证据时继续走 R1 的计算版本契约。

新增 `GET /api/v1/transactions/{id}` 供定位，支持相同双版本参数并校验用户归属。已撤销或不属于当前用户统一返回 404。保留原列表接口供既有调用方使用，不顺带改造核查和报表。

持久会话保存规范化条件、笔数、版本及有界展示结果；默认只保存首屏最多 20 笔的必要快照字段，不保存整次匹配集合。历史首屏展示已保存内容，详情和翻页必须版本核验；冲突后提示“账本已更新”，提供“重新查询”。时间与版本放“详情”，不重复添加永久“已保存”提示。

新工具结果扩展 R2 结构协议版本。旧 R2 结果继续可读；未知结构按现有安全降级处理。模型续问从服务端读取最后显式选中的查找条件，不能从旧结果数量推断当前事实；查找上下文与消费上下文分别保存，有歧义先澄清。新读取成功不覆盖历史结果，继续沿用 R2 有界上下文与轮次去重。

## 错误与日志

| 情况 | 展示与操作 |
| --- | --- |
| 参数错误（422） | 字段旁说明，如“最低金额不能大于最高金额”，保留输入 |
| 条件歧义 | 显示待选择字段或简短追问，不执行放宽后的查询 |
| 匹配为零（200） | “无匹配流水”，保留可编辑条件；不推断没有消费 |
| 容量超限（422，独立错误码） | “范围过大，请缩小日期或选择账户” |
| 历史/分页失效（409） | “账本已更新” + “重新查询”，旧数据不可继续修改 |
| 登录过期（401） | “登录已过期” + 登录入口；清理跨用户响应归属 |
| 详情不存在（404） | “流水已不可用”，返回查询结果 |
| 网络异常或超时 | 对应内容区显示“连接失败”或“查询超时” + 重试 |
| 服务故障（500/503） | “服务器异常”或“服务暂不可用”，不伪装成空结果 |

使用现有结构化错误契约，不按错误 message 猜类型。复用现有日志上下文；记录错误码、耗时和查询规模，不记录商户文本、备注、金额条件、完整请求体或结果。已有可用请求编号放折叠详情或复制入口；内部堆栈只留日志，不为普通校验错误增加详情卡。

## 评审补齐：完整导出、写入保护、条件恢复和核查证据

### 全部匹配结果导出

新增 `POST /api/v1/transactions/search/export`，接收规范化 filters 和必填的双版本，不接受 offset。搜索和导出调用同一匹配用例；同一可重复读快照中核验版本、取得完整匹配集合并生成 CSV。输出保留既有 CSV 字段和转义规则。

上限仍为 10,000 笔候选。版本失效返回 409，超限返回明确错误，均不返回 CSV。上限内先完成校验和文件构造，再发送成功响应；不得先下载成功文件头再在中途发现数据失效。前端使用服务端完整文件，删除 `ledgerCsv(filtered)` 作为导出数据来源的做法；详情页码不影响导出。

### 分类写入的服务端版本保护

`CorrectCategoryRequest` 新增必填 expected_revision。所有分类修正调用方同步传入对应读取快照的修订号；旧调用方缺失版本返回 422，不能为兼容而静默放过校验。实施时扫描全部调用方，必要时为原列表响应补充修订号。

仓储在现有用户行锁内读取当前 ledger_revision，与请求值比较；一致才继续校验流水归属、保存覆盖并递增修订号。读取必须刷新 ORM 中缓存的用户状态，不能把认证时的旧对象当作锁后版本。校验与写入在同一事务中完成。

不一致返回 409，保留用户选择但不自动再次提交。前端重读当前分类后由用户重新选择或明确确认。搜索语义版本保护查询重读；分类写入至少要求账本修订号，历史查询卡必须先通过双版本重读才能进入编辑，不能直接使用持久首屏快照发起修改。

### 会话查找条件的保存与恢复

为 assistant_conversations 新增可空 `search_context` JSON 与 `context_version` 整数（默认 0），不重用原 SpendingScope 字段。JSON 只保存有界规范化条件和结构版本，不保存金额结果或用户身份。为 assistant_turns 新增可空 `search_context`，冻结每轮受理时的查找条件。旧行初始化为 null，旧消费范围继续可读。

新增 `PUT /api/v1/assistant/conversations/{id}/search-context`：接收 filters（或 null 清除）及 expected_context_version；服务端验证条件和账户/批次归属，按现有用户→会话锁顺序校验未删除、版本一致后更新并递增版本，返回保存后的条件和新版本。此接口保存偏好，不调用模型，不查询或修改预算。

显式消费范围修改、查找范围修改和新轮次受理共享 context_version，避免多标签页互相覆盖。R3 新轮次携带预期上下文版本，受理时冻结服务端当前上下文；版本不一致返回 409，不自动重发问题。模型运行期间可修改下一轮条件，已受理轮次继续使用自己的快照；模型完成只写回该轮结果，不能覆盖后来选定的会话条件。旧客户端不得绕过版本保护覆盖新上下文，前后端需同批升级；旧结果读取兼容与旧请求写入兼容分别处理。

手动查询先成功、再保存条件。查询失败不改变已保存范围；保存失败显示结果但阻止以未保存条件续问。保存响应不确定时先重读会话版本和条件，一致则视为已保存，不盲目重试覆盖。多标签页冲突要求重新选择；客户端按用户、会话 ID 和请求序号隔离响应。

刷新后恢复已保存条件；手动查询的临时结果不恢复，也不自动调用模型，可点击“查询”重新获取当前结果。原助手历史卡保持原快照。删除会话与恢复准备必须清除新增上下文内容，去重墓碑不得残留商户查询文本；备份、还原、结构证据与离线清理同时覆盖新字段。

### 核查关联证据完整性

账本分页查询不触发原先整期间的 `api.reviews`。保留独立“异常核查”入口，用户展开时才读取；核查读取失败不阻止搜索结果展示。

新增面向账本的核查投影契约：输入原账本期间、当前页最多 20 个流水 ID、预期账本修订号。服务端必须在完整期间规则集合中计算核查，再选择与当前页 ID 有交集的核查项；不能对 20 笔流水单独运行规则，否则跨页成对异常会消失。每个返回项附其全部 transaction_ids 对应证据，包含不在当前页或不符合搜索条件的关联流水；前端不再用当前页 items 拼装证据。

为保留既有规则语义，首版允许展开核查时有界读取完整期间，最多 10,000 笔；超过上限仅让核查区提示缩小期间，不截断核查、不把没有核查结果解释为没有异常，也不影响已成功的精确搜索。核查项分页、证据逐项按需展开；单项关联证据超过展示页时支持独立证据分页并显示总条数，不能省略后仍标作完整证据。

核查规则集合、条目及证据使用同一快照并校验修订号；后续证据分页再次校验。确认继续走现有锁内完整重算和证据 key 校验，新增预期修订号校验以拒绝旧事实确认。独立核查页面保留原接口语义，不改变其规则范围。

## 验收门槛

- 固定合成数据使用人工独立列出的预期交易 ID 集合：精确/区间金额、符号、日期端点、多币种、账户、同名账户、分类覆盖、批次、商户/备注区分、全角/大小写/连续空白、百分号与下划线字面匹配均正确。
- 明确验收退款到账与原消费跨月、已确认转账/重复仍可找出；原消费分类不改变查找集合语义。输出不包含实际消费合计。
- 0、20、21、10,000、10,001 笔边界；相同时间流水稳定分页，无重复/遗漏；用户越权账户、批次、详情及版本请求不泄露数据。
- 导入撤销、分类修改和关系修改后的分页返回冲突；不能把旧详情当作当前可写对象。切换条件、前进后退、重试、退出登录、切换账号时迟到响应不能覆盖新状态。
- R2 刷新及重新登录恢复可读取新结果；旧协议仍可读；恢复和修改筛选不触发预算写入或自动重放模型请求。
- 无模型也能完成“手动筛选 → 分页 → 详情 → 返回”；助手使用固定模型决策验证工具契约，真实模型另备至少 20 个包含明确、歧义及不支持条件的场景。未获外部调用授权时仅交付场景和确定性结果，模型语义验收标为未运行。
- 浏览器验收中文/英文、1440px/375px、长商户名、空结果、加载失败、失效重查；助手宽度稳定，无横向溢出，键盘可完成表单提交与详情返回。合成数据库验证不冒充真实账单兼容性验证。
- 测量 1,000 与 10,000 笔候选下的冷/热查询、第一页/后续页、单请求/并发 5 的 P50/P95 和返回大小，记录 SQL 计划。暂定本机热查询单请求 P95 ≤ 500ms 为优化目标，未达标先分析证据，不通过扩大上限或截断结果达标。
- 导出验收至少含 21 笔及多页集合：CSV 行数与完整独立预期集合一致，任意页触发结果相同；导出期间版本冲突、容量超限和服务错误不产生部分成功文件。
- 两个会话同时修改同一流水分类，旧修订提交必须返回 409；认证读取与取得行锁之间发生修改也必须被拒绝；缺少版本的调用方不能静默继续写入。
- 手动改条件后刷新、继续提问、切换会话、多标签冲突、保存响应丢失、模型迟到完成和删除并发均覆盖。临时结果与已保存条件分开断言，未保存条件不能成为服务端续问范围。
- 同一核查的关联交易分布在不同搜索页或被文本条件排除时，核查仍出现且能查看全部关联证据；核查容量失败与搜索成功独立，旧版本核查确认被拒绝。
- 新上下文字段覆盖空库升级、已有 R2 数据升级、迁移往返、备份还原、恢复准备及删除墓碑检查；旧结果可读，新上下文不会从已删除会话残留。
- 运行 `make verify`、原业务与交互回归、新 `verify-search` 及会话回归；迁移与恢复在本地隔离库验证。真实模型、生产数据库与部署验收单列。
