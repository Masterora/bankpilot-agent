# R4：同口径消费比较

设计日期：2026-09-21。代码基线：`main@173f62a`。状态：已在本地工作树实现；实际通过项与缺项见 [R4 交付记录](R4_ACCEPTANCE.md)，尚未完整验收或发布。

## 目标与价值判断

用户问“九月比八月多花的钱，主要在哪些分类？”时，BankPilot 应直接给出可核对的差额，而不是让模型分别查询两个月后自行做减法。

本轮交付一条完整路径：**提出双月比较 → 查看总差额和分类贡献 → 打开任一分类的两期流水证据 → 返回原比较结果**。

它解决的不是普通图表展示，而是三个实际问题：

- 两个月必须使用同一套重复、本人转账、退款和分类规则，避免口径漂移。
- 总差额必须能由分类差额严格对账，每个主要变化都能落到流水证据。
- 未结束月份、缺少导入和退款变化必须明确展示，不能被模型解释成消费习惯或节省。

完成标准是用户能回答“多花了多少、由哪些分类组成、具体是哪几笔”，且金额、版本和用户隔离全部由确定性服务控制。

## 本轮范围

### 交付

- 比较两个不同月份、同一币种的实际支出。
- 服务端统一计算消费、已确认退款、实际支出及分类差额。
- 已结束月份比较完整自然月；目标月为当前月时，默认两边比较截至同一日。
- 助手新增只读 `compare_spending` 工具，模型只负责识别月份和币种；工具成功后由服务端直接形成确定性结果，不再让模型复述或计算金额。
- 比较结果随会话保存，刷新后仍显示当时的确定性结果。
- 每个分类可分别查看基准期和目标期的逐笔贡献，复用现有账本定位。
- 账本或计算规则变化后，历史合计继续可读，新的证据读取明确失效并要求重新比较。

### 不交付

- 不增加独立比较页面、通用分析仪表盘或新的数据库表。
- 不比较不同币种，不自动换汇或跨币种求和。
- 不做商户别名合并、原因推断、预算建议、预测、年化或“应该削减多少”。
- 不支持任意日期区间、周同比、同比季节调整或多于两个期间。
- 不把流水条数称为消费次数，不把金额相关性解释为生活行为原因。
- 不向模型发送商户、备注或逐笔流水，也不增加任何金融写操作。

## 比较口径

### 月份与方向

比较输入使用 `baseline_month`、`target_month` 和 `currency`。两个月都必须是月初，且 `baseline_month < target_month`。如果用户只说“比较八月和九月”，按较早月份为基准、较晚月份为目标；如果月份或币种无法唯一确定，助手先澄清。

差额方向固定为：

```text
差额 = 目标期实际支出 - 基准期实际支出
```

正数表示目标期支出增加，负数表示减少，零表示持平。界面始终同时显示月份和“增加 / 减少 / 持平”，不能只依赖正负号或颜色。

### 实际日期范围

服务端根据业务时区和受理时保存的 `business_date` 决定范围：

| 情况 | 基准期 | 目标期 |
| --- | --- | --- |
| 目标月已经结束 | 基准月完整自然月 | 目标月完整自然月 |
| 目标月是当前月 | 月初至当前日序号，超过该月末时取月末 | 月初至业务日期 |
| 目标月在未来 | 拒绝，不生成零值比较 |

例如业务日期为 3 月 31 日，比较 2 月和 3 月时，实际范围为 2 月 1–28/29 日与 3 月 1–31 日。结果必须显示两个实际日期范围，不描述为完全等长。首版不开放手动截止日；需要任意截止日时再扩展明确参数，避免模型静默选择口径。

### 金额规则

比较复用 `services/spending.py` 的贡献规则：

- 已确认重复记录和本人转账不计入消费。
- 支出以正贡献计入；已确认退款按到账月、原消费当前分类计为负贡献。
- 未确认退款不提前抵扣；收入不进入消费比较。
- 用户分类覆盖优先于规则分类；不同币种完全隔离。
- 每个月或截止范围超过现有 10,000 笔容量时，整个比较失败，不返回部分差额。

每一侧及每个分类都计算：

```text
实际支出 = 消费金额 - 已确认退款
分类差额 = 目标期分类实际支出 - 基准期分类实际支出
总差额 = 目标期总实际支出 - 基准期总实际支出
```

必须满足以下确定性不变量：

```text
所有分类实际支出之和 = 当期总实际支出
所有分类差额之和 = 总差额
总差额 = 消费金额差额 - 退款金额差额
```

分类集合取两期出现分类的并集。某分类仅一侧出现时，另一侧显示零，但“零”不能替代导入覆盖提示。

### 覆盖与零值

每一侧返回实际查询起止日期、该币种流水数量、已观察到的最早/最新入账日期和贡献条数。查询范围与已观察流水范围必须分开标注；覆盖状态仍是“未认证”，系统不声称账单完整，也不把首尾日期之间没有流水解释为缺失。

- 两侧都有该币种流水：正常比较。
- 一侧没有该币种流水：仍展示数学差额，但紧邻结果标出该侧“尚无已导入流水”，模型不得解释为真实的新增或节省。
- 两侧都没有该币种流水：返回无可比较数据，不生成“持平 0 元”的结论。
- 有流水但实际支出为零：保留为合法零值，并与“没有导入”区分。

## 领域契约

在 `domain/spending.py` 中扩展现有消费契约，不新建第二套金额模型：

```text
SpendingComparisonScope
  baseline_month
  target_month
  currency

SpendingComparisonPeriod
  month / start_date / end_date
  gross_spending / refund_offset / net_spending
  contribution_count / coverage

SpendingComparisonCoverage
  transaction_count
  earliest_transaction_date / latest_transaction_date

SpendingCategoryComparison
  category
  baseline_gross / baseline_refund / baseline_net / baseline_count
  target_gross / target_refund / target_net / target_count
  delta

SpendingComparison
  scope / baseline / target
  gross_delta / refund_delta / net_delta
  categories
  data_status
  ledger_revision / calculation_version / comparison_version / calculated_at
```

`data_status` 仅取 `comparable`、`baseline_missing`、`target_missing`、`both_missing`。它描述导入事实，不评价消费好坏。

比较语义使用独立 `comparison-v1`；底层贡献继续携带 `spending-v1`。分类、退款、排除规则改变时更新 `spending` 版本；日期截断、差额方向、分类并集或排序语义改变时更新 `comparison` 版本。

逐笔下钻使用 `GET /api/v1/assistant/turns/{turn_id}/comparison-evidence`，不接受客户端重新提交月份、截止日期、币种或版本。查询仅包含 `side`（`baseline` / `target`）、`category` 和 `page`。服务端按当前用户读取已完成轮次，要求 `result_version = 3`，再从保存的唯一 `compare_spending` 结果中取得可信的实际范围、币种、账本修订和两个计算版本。分类必须存在于该轮比较的分类并集中。

响应返回该侧该分类的稳定分页证据。这样证据严格绑定当时保存的比较，不会因客户端参数漂移把截至同日比较打开成整月明细，也不改变现有完整月 `SpendingScope` 的含义。其他用户的轮次、非比较轮次、未知分类或不匹配的结果结构一律不读取。

## 服务与一致性

`services/spending.py` 增加范围读取和比较函数。现有预算与单月消费调用保持完整月默认行为；比较和比较证据显式传入服务端解析后的 `end_date`。

两期计算在同一个可重复读事务中完成；计算结束释放快照，轮次保存继续使用现有独立完成事务与截止时间检查，证据读取另开快照：

```mermaid
flowchart LR
    Q[模型选择比较工具] --> V[校验月份 币种 业务日期]
    V --> S[读取同一账本修订快照]
    S --> B[计算基准期贡献]
    S --> T[计算目标期贡献]
    B --> D[分类并集与差额不变量]
    T --> D
    D --> R[服务端形成结果卡并保存到轮次]
    R --> E[按轮次和侧别读取分类逐笔证据]
```

两侧必须得到相同 `ledger_revision` 和 `spending-v1`。任一侧超限、读取失败或不变量不成立时整次失败。不得先返回一侧再补另一侧，也不得让模型汇总两个单月结果。

证据接口从轮次保存结果取得并重新核验 `ledger_revision`、`spending-v1` 和 `comparison-v1`。任何一个不一致返回 409；历史聚合卡保留，但“查看构成”停用并提供“重新比较”。

## 助手与历史结果

新增严格工具：

```text
CompareSpending
  kind = compare_spending
  arguments = SpendingComparisonScope
```

提示词要求比较问题使用该工具，禁止连续调用两个单月工具后自行计算差额。`compare_spending` 是终止型只读工具：服务端计算完成后直接返回本地化的中性说明和结构化比较卡，不再发起下一次模型决策。该轮最终证据只包含这一份比较聚合，丢弃此前工具观察，不保存此前搜索流水，也不生成预算提案。模型历史中的这段说明只含月份、币种和查看卡片的指引，不包含比较金额。

确定性保证从比较工具被选中或结构化重新比较请求被受理开始。自由文本的意图识别和工具选择仍由模型完成：误选单月工具或直接作答属于模型验收失败，不能声称终止型工具已阻止所有此类错误。只有包含服务端比较结果的轮次才呈现比较卡；普通文字不冒充比较成功。固定网关验收必须显式注入误选两个单月工具、直接回答及先搜索再比较的决策序列，分别记录路由缺陷和成功比较路径的金额、隐私保证。

只支持最新契约：请求协议升级为 `protocol_version = 4`，结果结构升级为 `result_version = 3`。删除旧请求解析、旧结果解码、旧文本降级和旧本地恢复格式的兼容分支，不做旧结果转换或双版本适配。

所有助手接口（提交、请求查回、会话列表/详情、历史分页、轮询、证据、上下文更新、提案操作及删除）统一要求 `X-Assistant-Protocol: 4`；缺失或不同值在执行业务前返回 409 `assistant_protocol_upgrade`，提交体中的协议也必须为 4。Web 请求封装统一发送该头。前后端同批更新，已打开的旧页面必须刷新，服务端不给旧页面返回新结构。

新客户端只渲染结果版本 3；既存旧轮次只返回身份、问题、状态等元数据及 `assistant_result_unavailable` 标记，不返回旧结果正文、证据或提案，也不送入模型历史。已有数据不因取消兼容而自动删除。旧本地待处理记录不自动重放，不清除未确认请求的标识；明确提示版本已更新，需重新打开会话核对。未知未来版本同样拒绝解释。

R4 不新增“当前比较上下文”数据库字段；比较结果随轮次保存，证据按钮通过轮次 ID 下钻。自然语言追问缺少明确范围时先澄清，不能从历史文字猜测月份或分类。

### 重新比较

比较卡使用专用“重新比较”按钮，替换现有单月通用重查入口。按钮通过现有 `POST /api/v1/assistant/turns` 提交新的 `request_id`、当前会话及 `expected_context_version`，并增加可选 `recompare_of` 原轮次 ID；它与 `retry_of` 互斥。该模式不接受调用方提供的新月份、币种或消费范围，不调用模型。

受理事务核验原轮次属于当前用户和当前会话、已完成且为最新结果结构，从其比较结果取双月和币种；按新轮次受理的 `business_date` 重新确定截止日期，并直接执行共享比较服务。跨日更新到新日期，跨月后目标月已结束则按完整月比较。按钮旁说明“按当前日期重新比较”，新卡展示实际日期；旧卡保持原结果。

请求摘要包含 `recompare_of`，相同请求 ID 重放读取原轮次，不再次刷新业务日期或计算。沿用现有轮次幂等、上下文版本、截止时间、删除竞争和完成令牌保护。新轮次结果保存完整范围，无需新增数据库列；受理期间在内存中冻结解析出的范围，失败后由用户发起新请求。重新比较及打开其证据不改变已选择的消费或搜索范围。

## 界面与交互

比较结果放在现有助手答案中，不增加导航项。卡片结构为：

1. 标题：`2026-09-01—09-30 对比 2026-08-01—08-31 · CNY`。
2. 总差额：明确显示“实际支出增加 / 减少 / 持平”及金额。
3. 分解：基准期、目标期的消费、退款和实际支出。
4. 覆盖：查询日期范围、两侧流水数量及已观察到的最早/最新日期，缺失侧紧邻总差额提示。
5. 分类列表：按 `abs(delta)` 降序，相同差额按稳定分类代码排序。

分类行同时显示分类名、基准值、目标值、差额及方向文字。可用以零轴为中心的短条辅助扫描，但精确数值和方向文本始终可见；颜色不单独表达增加或减少。不引入图表依赖。

每个分类提供两个明确按钮，例如“查看八月构成”和“查看九月构成”。按钮只携带当前轮次 ID、侧别和分类，点击后在助手详情层打开对应期间的分页证据，继续复用账本流水定位；返回时恢复比较卡滚动位置。窄屏按“分类 → 两期金额 → 差额 → 证据按钮”纵向排列，不出现横向表格滚动。

UI/UX 约束：

- 可交互目标至少 44×44px，键盘可以打开证据和返回。
- 列表使用稳定分类代码作为 key，不以数组索引绑定动态分类。
- 错误使用 `role="alert"`，加载和保存状态使用可读状态文本。
- 增减同时使用箭头或文字与数值，不能仅用红绿；普通文本保持至少 4.5:1 对比度。
- 历史卡标注计算时间和“当时比较”，但不重复堆叠永久提示。

## 错误行为

| 情况 | HTTP / 展示 |
| --- | --- |
| 同月、顺序错误或月份格式错误 | 422，保留问题并提示选择两个不同月份 |
| 目标月在业务日期之后 | 422，提示未来月份不可比较 |
| 币种缺失或歧义 | 助手澄清，不自动跨币种合计 |
| 任一期间超过容量 | 422，提示缩小范围；不返回部分结果 |
| 两侧均无该币种流水 | 200，无可比较数据；不显示“持平” |
| 单侧无流水 | 200，显示差额及覆盖警告，不解释原因 |
| 证据版本过期 | 409，保留历史合计并要求重新比较 |
| 客户端协议缺失或不是版本 4 | 409 `assistant_protocol_upgrade`，刷新后再操作 |
| 历史结果不是版本 3 | 仅显示结果不可用状态，不解析旧正文或证据 |
| 轮次不属于当前用户、不是已完成比较或分类不在结果中 | 404/422，不接受客户端补写范围 |
| 模型输出无效或不可用 | 使用现有错误契约，保留用户输入 |
| 数据库或服务故障 | 503/500，不降级为零金额或空结果 |

日志记录工具名、耗时、两侧读取规模和错误码，不记录问题正文、商户、备注或逐笔结果。

## 验收门槛

### 确定性金额

- 固定夹具独立列出两期全部贡献 ID、分类、消费、退款和实际支出，测试预期不调用生产计算函数生成。
- 分类并集、总差额、消费差额、退款差额满足三项不变量；正差、负差、零差和合法负实际支出均覆盖。
- 已确认重复、本人转账、跨月退款及原消费改类符合现有 `spending-v1`；未确认关系不影响结果。
- 同币种隔离、用户隔离、无数据与零支出区分；单侧缺数据不被表述为真实增长或下降。
- 已结束月份使用完整自然月；当前月使用相同日序号；2 月、30 天月份和闰年显示实际截止日期。
- 10,000 条边界成功，任一侧 10,001 条明确失败且无部分比较。

### 版本与历史

- 比较读取期间并发修改不会混合两个修订；完成后的分类修改、导入撤销或关系变更使证据读取返回 409。
- `spending-v1` 或 `comparison-v1` 不一致均拒绝重读。
- 只接受请求协议 4、只解析结果版本 3；旧页面的提交、查回、历史读取、轮询及写接口全部拒绝。旧结果不返回正文、证据或提案，不进入模型历史；未知版本同样处理。最新结果刷新、重新登录和历史分页不重新调用模型。
- 重新比较保留双月与币种，跨日/跨月按新受理日期计算；请求重放不改变首次受理日期。原轮次归属、结果类型、上下文冲突、删除竞争和迟到完成均有固定回归。
- 证据接口只能从当前用户的已保存版本 3 轮次解析范围；篡改侧别、分类或引用其他用户/非比较轮次均被拒绝。
- 比较不创建提案、不写预算、不改变消费或搜索上下文。

### 助手与隐私

- 固定模型决策覆盖明确双月、缺月份、缺币种、同月、未来月和跨币种请求。
- 模型选择 `compare_spending` 后不再收到比较结果，也不发生后续模型调用；最终持久结果仅保留比较聚合，即便此前执行搜索也不得保存商户、备注或逐笔流水。结构化重新比较的模型调用次数为零。
- 误选单月工具或直接作答计为路由失败，不能计入比较成功率；模型历史不注入比较金额，结果卡与中性说明不使用模型生成的差额。
- 真实模型另准备至少 20 个中英文场景，单独统计工具选择、月份/币种提取与澄清准确性；未获外部用量授权时标记未运行。

### 界面

- 中文和英文、1440px 与 375px 验证总差额、覆盖警告、长分类文案、无数据、失败及版本失效。
- 分类按绝对差额稳定排序；颜色关闭后仍可理解增减，键盘可打开两期证据并返回。
- 两期证据分页金额与分类行对应侧合计一致；从流水详情返回后恢复比较卡及证据页位置。
- 快速切换会话、证据侧和重新比较时，迟到响应不能覆盖当前视图。
